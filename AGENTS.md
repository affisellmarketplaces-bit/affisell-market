## Merchant custom domains & storefront theme

- **DNS**: merchants set `CNAME` → `STORE_CNAME_TARGET` (default `cname.affisell.com`), then **Activate domain + SSL** in Store profile (`/dashboard/*/settings/store`) — or wait for cron auto-activation.
- **Auto subdomain**: on signup, `{slug}.{AFFISELL_STORE_HOST_SUFFIX}` (default `shops.affisell.com`) — same catalog as `/shops/{slug}`; wildcard DNS on Vercel required in prod.
- **Subdomain HTTPS is decided by a real TLS handshake, not by Vercel's flag** (`lib/store-subdomain-reachability.ts`, applied in `lib/store-subdomain-provisioning.ts` and the 30-min cron). `Store.subdomainVercelStatus` can be `unreachable` = Vercel says configured but a browser cannot open it; the public URL then stays on `/shops/{slug}` and recovers by itself once the handshake works. A network blip (timeout/reset) never flips a status. Probe runs in production only (`AFFISELL_SUBDOMAIN_PROBE=0|1` to force). Diagnose: `npm run verify:store-domains` (add `-- <slug>` for one store).
- **Known infra constraint (Cloudflare)**: Cloudflare's free Universal SSL covers `affisell.com` and `*.affisell.com` only — **not** `{slug}.shops.affisell.com` (two labels) → `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`. Fix: order an Advanced Certificate for `shops.affisell.com` + `*.shops.affisell.com` (SSL mode "Full"), or set the `*.shops` DNS record to DNS-only → `cname.vercel-dns.com` (Vercel then certifies each store host).
- **Routing**: `middleware` calls `/api/store/resolve-host` and rewrites verified hosts to `/shops/:slug` (affiliate) or `/store/supplier/:slug` (supplier). Dashboard/checkout paths redirect to the platform origin.
- **Vercel SSL (1-click)**: `VERCEL_API_TOKEN` + `VERCEL_PROJECT_ID` → `POST /api/store/verify-domain` registers hostname + www redirect on the Affisell Vercel project. Cron `GET /api/cron/sync-store-vercel-domains` (every 30 min via GitHub Actions) auto-verifies DNS + retries pending SSL. Preflight: `npm run verify:store-domains`.
- **Theme**: `Store.storefrontTheme` JSON (`primary`, `accent` hex) — **Brand Studio** (`/dashboard/affiliate/brand-studio`, `/dashboard/supplier/storefront`); applied via `StorefrontThemeStyles` on public shops.
- **Status**: `Store.vercelDomainStatus` (`active` | `pending` | `failed` | `skipped`); polled in UI via `GET /api/store/domain-status`.
- **Smart header** (live `/shops/{slug}` only — `StorefrontBuyerChrome smartHeader`, Brand Studio preview keeps the plain header): `position: sticky` can't work there (the header's container is as tall as the header; mobile html/body are `overflow-x: hidden`), so the header is `fixed` + an in-flow spacer of the same height (zero layout shift). Away while reading down, back as a compact bar (trust rail folded via `[data-chrome-rail]` in `globals.css`) on the way up, full again near the top; stays visible while the menu is open or focus is inside it; `prefers-reduced-motion` keeps the static header. Mobile-browser hardening: scroll offsets past the real end of the page (iOS rubber-band) and scroll shifts that follow a viewport resize (iOS toolbar collapse, rotation) are never read as a scroll direction. Pure logic + tests: `lib/storefront/header-mode.ts`; hooks: `hooks/use-header-mode.ts`.

## Listing readiness — product safety (GPSR) & identity

- **One definition of "ready to publish"** for a physical product: `lib/listing-compliance/evaluate.ts` (pure, shared by the API and the forms). Checks PRESENCE/FORMAT of the declared data, never its truth: manufacturer name / address / email / country, an **EU responsible person when the manufacturer is outside the EU**, GTIN check digit; brand and missing GTIN are advisory only. Digital goods are out of scope.
- **Rollout switch `LISTING_READINESS_MODE`** = `off` | `warn` (**default**) | `enforce`, read per request (flip it on Vercel, no code deploy). `warn` only logs `[listing-readiness]` lines (what WOULD be refused); `enforce` answers **422 `listing_not_ready`** with language-neutral codes, before anything is written. It applies to **new publications only** (create live, draft → live, CSV rows): drafts and edits of listings that are already live are never blocked, so legacy listings stay editable. Wired in `POST /api/supplier/products`, `PUT /api/supplier/products/[id]`, `POST /api/supplier/bulk-import/commit` and the legacy quick-upload `POST /api/products/upload` (helper `lib/listing-compliance/gate.server.ts`, never throws).
- **Before flipping to `enforce`**: run `npm run report:listing-readiness` (READ-ONLY; uses the DATABASE_URL of `.env.local` — possibly production) and watch the `[listing-readiness] result: would_refuse_if_enforced` logs. Every UI that publishes can comply: classic form, guided wizard and Express wizard (`ListingComplianceSection`; Express opens it on a 422), CSV template columns (`manufacturer_*`, `eu_rep_*`, `gtin`). Automated imports that create products without a supplier action (integration sync, `supplier-products-import-exec`, Dropforge, import-from-url) are NOT gated yet: the AliExpress paths create drafts, so they hit the gate when published, but the others should be audited before enforcing.
- **Storage = `ProductAttribute` rows with reserved keys** (`lib/listing-compliance/keys.ts`: `brand`, `ean`, `mpn`, `gtin_exempt`, `gpsr_*`), **not new columns on `Product`**: the migration used to be warn-only in the Vercel build (today it is applied by hand BEFORE the push and the build only verifies, see « Migrations » below), so a column on the hottest table could reach production code before the database has it. The only new table, `SupplierComplianceProfile` (the supplier's reusable manufacturer / EU-rep defaults), is isolated and accessed defensively (`profile.server.ts`: a missing table = "no profile", never a crash).
- **The profile is a default to OFFER, never applied silently**: a dropshipper is rarely the manufacturer, so each product still carries — and the supplier still confirms — its own values (one-click prefill buttons in `GpsrFields`). Settings page: `/dashboard/supplier/settings/compliance`.
- **`managedAttributeKeys`**: `PUT /api/supplier/products/[id]` replaces the whole attribute set with what the form sends; a form only knows its category's attributes, so saving used to delete everything else (guided-wizard manufacturer / material / dimensions). A form now declares the keys it owns and the rest is preserved (`mergeManagedProductAttributes`). Without the declaration the legacy contract is unchanged.
- **Buyer-facing labels are translated from the KEY** (`productSpecs.keys.*`, `lib/listing-compliance/spec-labels.ts`): rows were stored with the French label the wizard wrote. Regulatory rows are excluded from product highlights (`highlight: false`).
- **Duplicates** (`GET /api/supplier/products/duplicate-check`): the supplier's OTHER products with the same GTIN, main photo or name — advisory only; other suppliers' products are never considered.
- **Hydration**: the country `<select>` is filled only after hydration (`useHydrated`): ICU country names/sort order differ between Node and the browser and caused a React hydration mismatch.

## Supplier add-product — earnings preview, photos, drafts (guided wizard)

- **What a supplier really receives** (`lib/supplier-earning-preview.ts`): `price − round(price × commission%) − round(price × feeBps / 10 000)`, i.e. the reseller's commission is paid OUT OF the supplier's price and Affisell's category fee comes on top (catalogue channel; auto-buy adds a surcharge and uses the AliExpress wholesale — not modelled). `lib/__tests__/supplier-earning-preview.test.ts` compares it with the real settlement functions (`computeMarketplaceOrderSettlement`, `buildPhase1FeesForOrderLine`, `netSupplierPayoutCents`) over 700 price/commission/fee combinations: if you change settlement, that test must keep passing. The classic form's "Simulation live" card used to show the full catalogue price as "Vous recevez / vente" — now it shows the net, and "(avant frais Affisell)" while the category is unknown.
- **Fee rate**: `GET /api/supplier/category-affisell-commission` now also returns `supplierCatalogFeeBps` — the rate THIS supplier pays (a negotiated `User.supplierFeeBps` / `supplierFeeBpsCatalog` wins over the category grid, same resolution as at settlement). Client hook: `useSupplierFeeBps` (`null` while unknown → the UI never invents a rate).
- **Guided wizard photos**: up to `GUIDED_MAX_PHOTOS` (8), main photo first (make-main / remove / promote-next), photo-quality hint reused from the classic form (`SupplierPhotoQualityHint`). A picked `FileList` is copied before the input is cleared (it is live in Safari/Firefox).
- **Guided wizard local draft** (`lib/supplier-guided-draft.ts`): autosaved to localStorage (800 ms debounce) under `affisell:guided-add-draft:v1:<supplierId>`, offered back on the next opening ("Resume / Start over") — NEVER restored silently, and the stored draft is not overwritten by the empty form while the offer is pending. Everything read back is re-sanitised (https photo URLs only, whitelisted attribute keys, category checked against the wizard's list, numbers as numbers); scoped to the supplier id; expires after 7 days; cleared on publish, on a server draft save and on "Start over".
- **Shipping is included in the supplier's price — buyers are never charged shipping.** Checkout (`lib/marketplace-checkout.ts`) carries product lines only and the settlement has no shipping term, so a "shipping cost" or "free-shipping threshold" a supplier typed in was never paid by anyone. Hence: no shipping-cost input in the classic form, no `shipping_cost_eur` column in the CSV template (an old file that still has a non-zero value parses, stores nothing and gets a `shippingCostIgnored` warning), no "Free shipping over €X" on the PDP, and `SupplierShippingIncludedNotice` (`components/supplier/shipping-included-notice.tsx`, `supplier.shippingIncluded.*` in 8 locales) under every price field telling suppliers to build their delivery cost into the price. The `Product.shippingCost` / `freeShippingThreshold` columns, the API parser (`lib/supplier-product-shipping.ts`) and stored values are untouched (no migration; PUT leaves them alone because forms no longer send them). The `freeShipping` flag stays as a badge + marketplace filter only (it does not change what a buyer pays). **If buyer-paid shipping is ever introduced** (Stripe `shipping_options`, VAT on shipping, supplier share, refunds), that is a money-path project that needs the accountant first — revisit these fields then.
- **Per-product return window (supplier decides, supplier pays — owner decision 2026-10-07)** (`lib/return-terms.ts`, `lib/return-terms.server.ts`): a supplier can offer 30/60/90 days (any whole number 15–90 via API) instead of the legal 14 — **extension only, never shorter**. Stored as the reserved `ProductAttribute` `return_window_days` (no row = 14 days; sanitised in `normalizeProductAttributesFromBody` for every route; kept by PUT's `alwaysKeep`; hidden from spec rows via `HIDDEN_SPEC_KEYS`). **Frozen at purchase** in the isolated table `OrderReturnTerms` (migration `20261007120000_order_return_terms`; one row per order, only written for an extension) by `recordOrderReturnTerms`, called from `scheduleMerchantOrderAlerts` AFTER the response — never inside the payment transaction, idempotent, never throws, only for orders created in the last hour — so shortening the window later never touches orders already placed. Readers (`return` route, buyer order list/detail) use `loadOrderReturnWindowDays*`, which fall back to the legal 14 days when the table is missing (apply the migration by hand: `DATABASE_URL='<url>' npm run schema:migrate -- --expect-endpoint <ep-id>`). The refund path is unchanged: the supplier approves the case and the refund is taken from their share (`supplierReturnLiabilityCents`) exactly like a legal-window return. Return shipping cost is NOT modelled (the buyer ships back with tracking, as before), so the page says "Returns accepted within N days", never "free returns". Form: `ReturnWindowField` in the classic form only (guided/Express keep the legal default); the PDP chip appears only for an extension. A category change in the classic form now keeps product-level values (identity, GPSR, return window) instead of wiping them.
- **Warranty — still a gap**: per-SKU `warrantyMonths` (advanced SKU table; `lib/product-warranty.ts`) feeds a badge the reseller can switch on (`showWarranty`), but the return flow stops at the return window, so a buyer has NO on-platform way to claim a warranty after it (reason `DEFECTIVE_OR_BROKEN` only works inside it). Showing "2-year warranty" therefore promises more than the platform can process; a warranty-claim path (same snapshot table + a claim reason accepted until `warrantyMonths`) is the follow-up, not built.

## Event spine (`lib/events/*`, table `AffisellTrackEvent`) — step S1 only

- **One table, two classes that must never be mixed** (`lib/events/names.ts`, the registry of every accepted event): **behavioral** (analytics: impression, click, view, search, cart, attribution touch) is recorded ONLY with the visitor's analytics consent and may carry `anonymousId`/`sessionId`/`channel`; **transactional** (the business journal: purchase, refund, return, delivery, review, creator listing add/remove) exists whatever the cookie choices are and NEVER carries a visitor identifier, a channel or a behavioral duration. `lib/events/row.ts` (`buildEventRow`, pure) enforces it; the `event_spine` migration repeats it as CHECK constraints, so a future code path that forgets still cannot store a visitor id on a business row.
- **Writer**: `recordEvents(events, { analyticsConsent })` (`lib/events/record.server.ts`) — idempotent (`eventId` unique + `createMany({ skipDuplicates })`; client UUID for behavioral, deterministic business key such as `purchase:{orderId}` for transactional), chunked, and it **never throws** (a failed analytics/journal write must not break the request). A database that is not migrated yet is logged once as `[events] schema_drift` — fix it by applying the migration (`npm run schema:migrate`, never a bare `prisma migrate deploy`), do not hide it.
- **Data minimisation lives in `lib/events/sanitize.ts` + `properties.ts`**: `properties` is NOT free-form (explicit allowed keys per event, one sanitizer per key); the search `query` is the only free text kept, and only as PRODUCT VOCABULARY — a query shaped like an e-mail, URL, phone/card/IBAN number, 5+ digit number (postal code, order number), identifier-like token (12+ chars mixing letters and digits), or street address is dropped WHOLE (fail closed, never half-masked), as is one over 8 words / 100 characters (valid GTINs are kept); person NAMES are not filtered on purpose (indistinguishable from brands — `lib/__tests__/events-search-query.test.ts` pins this limit); free-text or speculative keys (`variant`, `experiment_id`, `campaign_id`, `utm_term`) are not accepted at all and an inventory test fails when a key is added; referrers keep the HOST only; UTM values containing `@` are dropped; click identifiers (gclid/fbclid/ttclid) are never stored, only the platform. A browser can only send `clientEmittable` behavioral events and only via the strict schema in `lib/events/schema.ts` (no userId/creatorId/orderId/country/channel fields: the server derives them). Channel = deterministic rules in `lib/events/channel.ts` (no score).
- **Not wired yet**: nothing in the app calls the writer — the carousel / Pulse / agent checkout still use their legacy writes, and the 7 legacy readers (`eventType = 'view'` …) and `AffiliateProduct.clicks` are untouched. Wiring (ingestion endpoint, server emitters, attribution, `OrderAttribution`) is steps S2–S6, each to be validated by the owner.
- **Migrations**: explicit Prisma migration only — no runtime DDL, no `IF NOT EXISTS` to mask drift (`lib/__tests__/events-migration.test.ts` fails on it and on any schema/SQL mismatch). **Trap**: `prisma.config.ts` loads `.env.local` with `override: true`, so `DATABASE_URL="<branch>" npx prisma migrate deploy`, `npm run db:migrate` and `npm run migrate:deploy` really target the DEFAULT database, possibly production — never use them. **Deploy a schema with `DATABASE_URL='<url>' npm run schema:migrate -- --expect-endpoint <ep-id> [--confirm-production]` — by hand, locally, BEFORE the push (it refuses to run under Vercel)** and check it with `npm run schema:verify` (`scripts/schema-deploy.mjs`): explicit URL only (`.env*` is never read), `DATABASE_URL` / `DIRECT_URL` / `DATABASE_URL_UNPOOLED` must name the SAME endpoint, Prisma's own output must name it BEFORE anything is written, then `migrate deploy`, then the CATALOG is checked (`verify-event-spine` — `migrate status` alone proves nothing on a database that went through the old self-healing pipeline). **Every failure is a non-zero exit** (2 refused · 3 wrong target · 4 migration failed/unreadable · 5 verification failed). `scripts/prisma-explicit-db.mjs` is the low-level runner: `status`, `deploy`, and `resolve --rolled-back <name>` for a FAILED migration (P3009) — there is deliberately NO `--applied`, and a test fails if any file writes `_prisma_migrations` or runs `resolve --applied`. `prisma migrate diff` against this database also lists Medusa's tables as "to drop": never apply a diff or `db push`/`migrate dev` here. **Order**: migration in production → `schema:verify` → only then push the code (a push without that step is safe but fails: the Vercel build only VERIFIES and STOPS if the schema is missing — see below). `db:unlock` is a manual diagnostic (read-only by default; `--terminate --pid <n>` only for a stale session holding nothing but Prisma's migration lock `72707369`): it used to run before every build and killed any session holding any advisory lock, including the application's `pg_advisory_xact_lock` in payment / fulfilment / Medusa-sync transactions. Why the order matters (the legacy writers' `INSERT … RETURNING` lists all 22 columns), the pipeline, failure handling and the exact procedure: `docs/DEPLOY-SCHEMA-CHANGES.md`.
- **A developer machine never writes to PRODUCTION by accident** (S1.6.1). `.env` / `.env.local` hold the production URL and `@prisma/client` loads `.env` by itself, so a laptop-launched tool used to act on production silently (a unit test wrote fake AliExpress tokens into `PlatformOAuthCredential`). Rule: *developer machine (a secret `.env*` file is present — never on Vercel/Railway/CI) + a URL naming the production endpoint + no `AFFISELL_ALLOW_PRODUCTION_WRITES=<ep-id>` naming it* = refused. Applied in: every standalone script that creates a Prisma client (`scripts/lib/production-guard.mjs` → `assertNotProductionByAccident()` right before the client; a test fails for any new script that neither calls it nor is on the verified read-only list in `lib/__tests__/production-guard.test.ts`), the Prisma CLI write commands (`prisma.config.ts`), `lib/prisma.ts` / `lib/prisma-radar.ts` writes (`lib/developer-production-guard.ts`; reads still pass, the fulfillment client is judged on its own direct URL), and the auto-order worker (+ shared Redis). Vitest never sees `.env` (`vitest-env/no-real-datastores.ts`). `status` / `schema:verify` / `verify:event-spine` run in a server-enforced read-only session. Details: `docs/DEPLOY-SCHEMA-CHANGES.md` §10.
- **`next build` never writes to a database, and a local/CI `npm run build` cannot reach one.** `lib/build-write-guard.ts` is the outermost extension of every Prisma client (`lib/prisma.ts`, `lib/prisma-radar.ts`; a test fails if any other file creates a client): while Next reports `phase-production-build` (`isNextProductionBuildPhase()`), only known reads pass — create/update/delete, `$executeRaw*` and non-read-only `$queryRaw*` throw `BuildPhaseWriteBlockedError` BEFORE any connection; no override, and it does not depend on `VERCEL` / `VERCEL_ENV`. `npm run build` goes through `scripts/build-isolated.mjs`: on a real Vercel builder (`VERCEL=1` and NO secret `.env*` file in the working directory) nothing changes; elsewhere — including `vercel build` run on a laptop, which also sets `VERCEL=1` — every database/Redis credential (by name or by value shape, including those Next would load from `.env*`) and `SENTRY_AUTH_TOKEN` is set to an empty string for `next build` (Next never overrides a defined variable). `AFFISELL_BUILD_ALLOW_DB=1` keeps a NON-production database and refuses if any production URL is present. Next.js telemetry is off by default (`NEXT_TELEMETRY_DISABLED=1`). **Vercel pipeline (`scripts/vercel-build.mjs`, S1.6.1)**: `prisma generate` → `schema-deploy.mjs verify` (READ-ONLY: the database session itself is `default_transaction_read_only=on`) → `check:client-prisma` → `npm run build`, and it STOPS at the first failing step. **The Vercel build never migrates**: `BUILD_RUN_MIGRATIONS` is gone (not read, not in `vercel.json`) and `schema-deploy.mjs migrate` refuses to run in any Vercel context. Migrating is a separate step done by hand BEFORE the push (`schema:migrate -- --expect-endpoint <ep>`, staging for Previews too); a push whose migration was not applied fails at `verify` (exit 5) and the old code keeps serving. The build loads no `.env*`, runs no `db:unlock`, no repair SQL, nothing that marks a migration applied (`fix-p3009` / `deploy-repair.sql` and the cron's self-healing are gone; `/api/cron/migrate` is a read-only diagnostic). A Preview build whose database is not provably the staging branch (`ep-shy-wind-…`) is REFUSED; Production refuses staging/local; `VERCEL=1` on a developer machine is refused. Measured (network-denied build with every real credential loaded): no Redis/KV attempt; the only outbound requests were Next.js telemetry and the Sentry plugin's telemetry (both switched off now) plus the Sentry CLI source-map upload, which stays on Vercel (the three `SENTRY_*` variables exist in Production).

## Buyer identification — a typed identifier is not proof of ownership

- **Three entry points used to open a buyer session from an e-mail/phone alone**: `POST /api/auth/buyer-identify`, `POST /api/checkout/identified` (both via `lib/buyer-identify-session.ts`) and `POST /api/auth/post-checkout-buyer`. The last one trusted the e-mail on the Stripe session — which the PAYER types on Stripe's page (`lib/marketplace-checkout.ts` never presets `customer_email`) — so "it requires a paid session" was only a cost barrier, not a proof. A CUSTOMER session reaches `api/account/*` and `api/gdpr/*` (orders, returns, data export, account deletion).
- **Rule (`lib/buyer-account-ownership.server.ts`)**: a bare identifier never opens a session on an EXISTING account that has an owner (password, social login, verified e-mail) or history (orders, reward balance/ledger, reviews). A new or blank account keeps the one-step guest flow; a browser already signed in to that very account is let through. It fails closed (unreadable account = protected, database error = no session). In `post-checkout-buyer` the orders of the Stripe session being claimed are ignored, so a first-time guest who just paid still gets their session.
- **Refused buyers pay as guests**: `checkout/identified` runs `marketplaceCheckoutPOST` without `buyerUserId` (no reward redemption, nothing merged into the account); the order is still linked to the account by the e-mail Stripe collects. `buyer-identify` answers `requiresSignIn: true` with NO name and NO e-mail (the stored name must not leak) and the sheet shows `cart.identity.accountExists`; `post-checkout-buyer` answers 403 `sign_in_required` (the success page just skips the auto sign-in).
- **Known residual (Option A)**: a still-BLANK account (created, no order yet) can be claimed by whoever types its address first; the e-mail-proof flow (code by e-mail, `VerificationToken`) is the follow-up that closes it. The webhook still links an order paid with someone else's e-mail to that account (clutter, no data exposure). Tests: `buyer-account-ownership`, `buyer-identify-session`, `buyer-identify-routes`.

## Server-side fetch of user-chosen image URLs (SSRF)

- A listing's image URL is chosen by an affiliate or a supplier, and `GET /api/listing-card-image/[listingId]` is public: the server fetches it and hands it to `sharp`. **Never `fetch()` such a URL directly — use `fetchPublicImageBytes` (`lib/safe-remote-image.server.ts`).** `assertSafeOutboundUrl` alone only reads the hostname TEXT: `http://localtest.me/` (a public name resolving to 127.0.0.1), a name pointing at a cloud-metadata address, `https://[::ffff:127.0.0.1]/` or a redirect to an internal host all passed it.
- The helper checks the address at CONNECTION time (custom `lookup`, any private/loopback/link-local/CGNAT/ULA/mapped/NAT64/6to4/Teredo answer refuses the whole name, so DNS rebinding cannot swap it), judges IP literals itself (`net` never calls `lookup` for them), revalidates every redirect hop (3 max), and bounds the body (8 MiB while streaming) and the whole download (8 s). `isPrivateAddress` fails closed: anything that is not a well-formed IP literal counts as private.
- `listing-card-image.server.ts` then decides the format from the BYTES (`sniffUploadBytes`: JPEG/PNG/WebP/GIF only — SVG, AVIF/HEIF and TIFF, the decoders with the most `sharp` advisories, are refused and the card falls back to the placeholder) and calls `sharp` with `failOn: "error"`, `limitInputPixels: 40_000_000`; `data:` URLs get the same size cap before decoding.
- **Not migrated yet** (same hostname-only check): `lib/merchandise/generate-card.ts` (public `GET /api/merchandise/generate`) and `lib/photo-quality.server.ts`. Tests: `safe-remote-image`, `listing-card-image-source` (the older `listing-card-image.test.ts` covers the URL-picking helpers only).

## Virtual try-on — what is trusted and what is not

- **`?tryon=1` is honoured outside production only** (`lib/flags/try-on.ts`: `VERCEL_ENV`, else `NODE_ENV`). It is a query string anyone can add, so on the production deployment `TRY_ON_ENABLED=1` is the only way to turn the feature on. Previews and local dev keep the override for QA; for a full preview test set `TRY_ON_ENABLED=1` on the Preview environment (the API routes always use the strict flag `isTryOnFeatureEnabledStrict`, the override only shows the UI).
- **`POST /api/try-on/upload` is retired (410).** It was an anonymous upload to the PUBLIC blob store, unrate-limited, reachable with the kill switch off, and nothing called it. `lib/try-on/virus-scan.server.ts` is now unused.
- **The Replicate webhook body is never trusted** (`app/api/try-on/webhook/route.ts`). It used to check that some header existed (never its value) and finalise the job from `body.output`, which the server then downloaded and republished: a forged call was a full-read SSRF. Now only `body.id` is read, to find the job; status and output URL come back from Replicate with our token (`getTryOnJobStatus`). `REPLICATE_WEBHOOK_SECRET` is no longer read by the route — a real signature check (Svix) would only be defence in depth.
- **`fetchImageBytes` (try-on outputs and supplier-chosen garment URLs) goes through `fetchPublicImageBytes`**; `isVercelBlobUrl` tests the HOSTNAME, not a substring. `enforceTryOnIpRateLimit` falls back to the in-process limiter (5/min/IP) when Upstash is not configured — every call starts a paid Replicate prediction, so it must never be unlimited.
- **Not changed (privacy decisions for the owner)**: the shopper's selfie is stored on the public blob store (unguessable URL, deleted after the job and by the retention cron) unless `BLOB_TRYON_PRIVATE=1`; `GET /api/try-on?jobId=` / `prediction_id` answer without authentication (identifiers are not guessable). Tests: `try-on-flag-override`, `try-on-routes-hardening`, `try-on-image-fetch`, `try-on-rate-limit-fallback`.

## `proxy.ts` — reading the session, and what the proxy does NOT guard

- **Never call `getToken` directly in the proxy — use `readProxySessionToken(req, secret, secure)` and `resolveAuthSecret()` (`lib/proxy-session-token.ts`).** `getToken` throws `URIError: URI malformed` on a malformed `Authorization: Bearer` header when there is no session cookie (`@auth/core` 0.41.2, GHSA-xmf8), which made the page answer 500; the helper never throws and a missing secret or unreadable token is just "anonymous". `resolveAuthSecret` takes the FIRST NON-EMPTY of `AUTH_SECRET` / `NEXTAUTH_SECRET` like `env()` in `lib/auth.ts` — the proxy used `AUTH_SECRET ?? - **The proxy's role-guard block is UNREACHABLE for the protected areas, and has been since 2026-05-21** (`95e49eef8` + `d4de0f649`). `proxy()` returns at `if (isStaticAppPathname(pathname))` BEFORE it, and `dashboard`, `admin`, `crm`, `marketplace`, `login`, `affiliate`… are all in `RESERVED_LOCALE_SEGMENTS`. ## Stripe disputes, failed-webhook replay, cron failures (finalisation D7 / D2 / J1)

- **`charge.dispute.*` are handled by the dispute's STATUS** (`lib/stripe-dispute.ts`, called from the webhook processor; Stripe does not order events). Open (`needs_response`, `under_review`, `warning_*`, anything unknown) = every order of the charge is HELD: `Order.status = "disputed"` + an open row in the **dispute ledger = `ProcessedWebhook` rows with id `dispute:<dp_id>:<orderId>` and status `dispute_open|won|lost|closed`** (`lib/orders/dispute-hold.server.ts`, no migration; the previous status is kept in the `error` column as JSON). The payout release asks the LEDGER, not only the status, because tracking webhooks and supplier routes write `status: "shipped"` blindly: `process-transfers` (attempt stays PENDING, not cancelled), `triggerLightningPayout`, `payLegionOverrideForOrder`; `order-transfer-gating` has a `blocked_dispute` phase. Pure rules: `lib/orders/payment-state.ts` (`isOrderPayoutHeldForDispute`, `statusWhenDisputeOpens/Released`) and `lib/orders/dispute-state.ts`.
- **Won / closed without loss** restores the exact previous status and closes the row. **Lost** is applied automatically ONLY when the disputed amount equals what our orders of the charge account for (±1 cent per order): Connect transfer reversals (`reverseConnectTransfersForRefund`, key `<dp>:<order>`), an `OrderStripeRefund` row `reason: "dispute_lost"` (what lets the `retry-pending-clawback` cron finish), the clawback ledger, then `REFUNDED` / `REFUND_PENDING_CLAWBACK`. A partial / oversize / other-currency dispute keeps the hold open and alerts a human (`skipped`, `dispute_lost_manual_review:<reason>`): to release one by hand, settle the order then set that ledger row's status. Stripe's dispute fee is allocated to nobody. Effects first, terminal ledger row last (a replay after a mid-way failure converges); a terminal row is never reopened. Events to enable on the Stripe webhook endpoint(s): `charge.dispute.created`, `.updated`, `.closed`, `.funds_withdrawn`, `.funds_reinstated`.
- **Failed Stripe events are replayed after Stripe stops retrying** (3 days): `GET /api/cron/replay-failed-stripe-webhooks` (every 6 h, `lib/cron/replay-failed-stripe-webhooks.ts`): `failed` rows with an `evt_` id older than 72 h and younger than 30 days, oldest first, `stripe.events.retrieve` then the SAME `processStripeWebhookEvent`; cap 20 / 40 s; a still-failing event = one ops alert + HTTP 500 (red run); older than 30 days or gone at Stripe = `failed_expired` + alert once.
- **Crons**: `scripts/ci/run-crons.sh strict|lenient` runs the routes from `scheduled-crons.yml`. Money crons are `strict` (exit 1 on any curl error or non-2xx, no retry, no `|| echo WARN`) and their job has an `if: failure()` step (`scripts/ci/notify-cron-failure.sh`) that annotates and POSTs `/api/cron/notify-failure` (cron secret; the app posts to Slack/Discord through `lib/ops-webhook.ts`; body validated, bounded, mentions neutralised, `runUrl` must be a github.com Actions run; tolerant if the app is down). `lib/__tests__/cron-schedule-coverage.test.ts` fails on a `app/api/cron/*` route that is neither scheduled nor listed there as deliberately unscheduled with its reason, and on a money cron that is not strict: add the route to the workflow (or to that list) in the same change.

## Paid lines without an order (D6) and stock at purchase (G1)

- **A checkout line the buyer paid for but that produced no order is "UNALLOCATED"** (`lib/unallocated-line.ts`): listing gone (`listing_not_found`), listing inactive (`listing_inactive`), no explicit supplier commission (`commission_not_explicit`), or — in `enforce` mode — the stock ran out between checkout and payment (`insufficient_stock`). `fulfillMarketplaceStripeSession` used to `continue` / `return` with a `console.log`: the money stayed on the platform account, nobody was told, nothing retried. It now collects those lines during the transaction (they never stop the other lines of the same payment) and, AFTER it and after the response (`runAfterResponse`), calls `recordUnallocatedLines` (`lib/unallocated-line.server.ts`, never throws): (1) durable trace, (2) alert, (3) optional refund.
- **Trace = `AuditLog`, no migration**: `action` `payment.unallocated_line`, `entityType` `StripeCheckoutLine`, `entityId` `<session>:line:<index>` (single-line checkout = index 0), JSON `payload` (reason, paid / refundable cents, product ids, payment intent, store credit applied). The row id is deterministic (`unallocated-line:<key>`), so a webhook replay hits the primary key: no duplicate row, no second alert. Not `OpsSignal` (a Sentinel scan auto-resolves any signal no collector re-detects) and not `ProcessedWebhook` (the Stripe-event idempotency ledger, read by the replay logic). List them: `SELECT "entityId", "payload"->>'reason', "createdAt" FROM "AuditLog" WHERE "action" = 'payment.unallocated_line' ORDER BY "createdAt" DESC` (no Sentinel collector yet).
- **Alert** = `opsWebhookAlert` (needs `SLACK_WEBHOOK_URL` or `DISCORD_WEBHOOK_URL`) + `Sentry.captureMessage` (needs `SENTRY_DSN`) + a structured error log `unallocated_line`; only the first time a line is seen. It says the exact amount to refund and on which payment intent.
- **A single-line checkout's pre-created order is CLOSED when its line is unallocated** (`closeUnallocatedPendingOrder`: `status` and `paymentSettlementStatus` `CANCELLED`, the pair `isOrderClosedForPayout` reads). Left PENDING it was promoted to "paid" by the settlement that runs right after the fulfilment in the same webhook (`scheduleMarketplaceTransferAttempts`: webhook, `payment_intent.succeeded`, success page), which scheduled payouts and fed auto-fulfilment — and the reconcile cron revisited it every 30 minutes forever. A closed order is never fulfilled again (`skipped_order_closed`), never settled (`order_closed`), never re-synced (VAT sync skips it) and is not a PENDING row for the cron. A booking order is left alone. The buyer is not e-mailed: the alert is the only notice (decision to take).
- **Refunding an unallocated line — three ways, none touches the sibling order.** `handleStripeChargeRefundedWithCommission` classifies every refund of a charge that carries traced lines (`classifyRefundForCharge`, pure): (1) the marker `affisell_unallocated_line=1` (automatic refund); (2) a refund id already recorded on the line's proof row; (3) `metadata.orderId` set → that order; (4) a refund made BY HAND in the Stripe dashboard (no metadata) whose amount is EXACTLY the traced `refundableCents` of a not-yet-refunded line → that line (proof row `payment.unallocated_line.refunded`, `source: manual_dashboard`, an ops message "recognised by its amount"), unless the amount is also an order's total → ambiguous; (5) anything else → **ambiguous: applied to nothing, ops alerted** (on a charge with a single remaining order the handler used to judge it "fully refunded" from the charge-level `amount_refunded`: payouts clawed back, valid order cancelled, buyer e-mailed). A charge with no traced line behaves exactly as before. A closed skeleton order is not counted as a sale in that comparison. **So refund a lost line for EXACTLY the amount in the alert.** The proof row also stops a refunded line from ever becoming an order afterwards (`loadRefundedUnallocatedLineKeys`, read before the transaction). The trace is read by payment intent (`payload.paymentIntentId`); a database error there fails the webhook so it is replayed rather than guessing.
- **Automatic refund is OFF unless `UNALLOCATED_LINE_AUTO_REFUND=true`** (exact word; read per call, no deploy of code). It sends the line's HT amount + its share of the VAT back with `stripe.refunds.create({ payment_intent, amount })` (idempotency key `unallocated-line-refund:<key>`; before creating one it lists the payment's refunds and reuses a refund it already made for that line — Stripe forgets a key after 24 h and the proof-row write can fail). **Store credit**: it is consumed only when at least one line of the checkout became a sale (a checkout with no sale keeps the credit; the ledger key is per session so a later allocating replay redeems it once). A PARTIAL allocation redeems the whole credit: the share that belonged to an unallocated line is not given back automatically (it is in the trace, `appliedRewardCents`).
- **A cart with an unallocated line no longer corrupts its sibling orders' totals**: `syncOrderVatFromCheckoutSession` normalised the orders by THEIR OWN sum, so the surviving order absorbed the missing line's HT, VAT and total (a 30 HT line showed 50 / 10 / 60) and every refund / clawback figure was wrong. When the orders are fewer than the cart's lines each keeps its share of the whole session.
- **Stock — what the fields mean** (`lib/checkout-stock.ts`): `Product.stock` is a non-nullable Int; the PDP, boutique and SEO read 0 as sold out, **but not every surface does** (grid cards, discover feed) and the number is often not a maintained inventory (Express wizard writes 99, classic form defaults to 0, importers write 1 / 99 / 999). With advanced SKU lines the buyer sees `Product.variants.variantRows[].stock` and `Product.stock` is their sum. A product with variants only in the `ProductVariant` TABLE (`hasVariants`, no `variantRows`) is **unmanaged** (the buyer-visible stock is in that table, which checkout never reads or writes). Only PHYSICAL listings are managed. A product with variant rows whose line can not be tied to exactly ONE row is unmanaged too.
- **`CHECKOUT_STOCK_MODE` = `off` | `warn` (DEFAULT) | `enforce`**, read per request, same pattern as `LISTING_READINESS_MODE`. `warn`: the check before the payment only logs `would_refuse_insufficient_stock` and lets the buyer through; the fulfilment still takes the units but never below 0, never removes a paid line, and logs `[stock] would_drop` where it would have. `enforce`: 409 before the payment, and a paid line the stock can not serve becomes an unallocated line. `CHECKOUT_STOCK_GUARD=off` (also `0` / `false`) is the emergency valve and wins over the mode. **Before `enforce`: run `npm run report:checkout-stock` (READ-ONLY, uses the DATABASE_URL of `.env.local` — possibly production) and read the `would_drop` / `would_refuse` log lines.**
- **Before the payment** (`evaluateCheckoutStockGate`, shared by the cart checkout, the single-line checkout and `lib/agent-checkout.ts` — the agent's paid sessions reach the same decrement): in `enforce`, 409 `OUT_OF_STOCK` when nothing is left, 409 `INSUFFICIENT_STOCK` + `availableQty` otherwise, before the pending order and the Stripe session exist. These are Affisell's own codes: `OUT_OF_STOCK_VERIFIED` stays the supplier-probe refusal (its modal says "we just checked with our supplier" and hands out a coupon). The front end shows `cart.stock.*` (8 locales) from the code — in the buy-now hook (every caller: PDP, grid cards, discover, Pulse), the identity sheet and the cart page — never the raw code. `available` is the stock BEFORE the cart; lines sharing a product are counted together.
- **At payment processing** (`reserveStockInTransaction`, `lib/checkout-stock.server.ts`): inside the fulfilment transaction, right before the order is written (or the pre-created order is paid): `SELECT … FOR NO KEY UPDATE` on the product row (the per-session advisory lock only serialises ONE checkout session, never two buyers; **not** `FOR UPDATE`, which also blocks the foreign-key check of every order insert of that product, including the checkout that pre-creates the order), then for a product-level movement `updateMany … WHERE stock >= qty` (never negative), for a variant row a rewrite of the RAW `variants` json (only that row's `stock` changes — never write back the parsed copy) and `Product.stock` kept in step. A multi-line cart first locks its physical products ONE BY ONE in ascending id order, so two carts with the same products in opposite order can not deadlock. The confirmation e-mails of a cart (and of a fresh single order) are sent after the commit, never while a product lock is held. It commits or rolls back WITH the order; a replayed event finds the order already paid: no double decrement. **Still inside the transaction**: the Medusa sync (`syncMarketplaceOrderToMedusa`, HTTP, part of the order's atomic state).
- **Decisions for the founder (NOT implemented)**: (1) give the units back when an order is refunded / cancelled / returned (business rule: is a returned item resellable?) — until then every refund leaves the stock reduced (under-selling, never overselling); (2) a supplier saving the product form, or a catalogue / integration sync (`syncProductVariants` recomputes `Product.stock` from the table), overwrites the stock with its own value and resurrects sold units; (3) importers that write a nominal stock (AliExpress `stock > 0 ? stock : 1`, 99 / 999) with no scheduled refresh (J1): they will sell out after that many sales once enforced; (4) an unallocated line's buyer is not e-mailed; (5) a partial-allocation checkout's store-credit share. Both of (1) and (2) are why the default is `warn`.
- Tests: `checkout-stock`, `checkout-stock-client`, `unallocated-line`, `fulfil-unallocated-and-stock` (runs the real `fulfillMarketplaceStripeSession` AND the real settlement entry points on an in-memory database with rollback, `lib/testing/fake-checkout-db.ts`), `marketplace-checkout-stock-gate`, `agent-checkout-stock-gate`, `commission-refund-unallocated-line`, `stripe-sync-order-vat-unallocated`.

## AliExpress purchases — one gate for the three paths, and a margin floor (G2 + G3)

- **Every path that can place an AliExpress order calls `authorizeSupplierPurchase` first** (`lib/fulfillment/supplier-purchase-guard.ts`): the generic engine (`lib/suppliers/place-order-bridge.ts`, AliExpress adapter only), `lib/fulfillment/auto-buy.ts`, and `order.paid` / the manual `/api/orders/[id]/fulfill` route (`lib/aliexpress-fulfill-order.ts`). Five triggers still fire on every payment — on purpose; the gate, not the number of triggers, is what makes a double purchase impossible. **A new code path that buys on AliExpress MUST go through it** (lock → re-read → claim → margin), and must call `markSupplierPurchasePlaced` / `releaseSupplierPurchase` / `reportInDoubtPurchase` according to the supplier's answer.
- **How it works**: one transaction takes `pg_advisory_xact_lock(hashtext('affisell:supplier-purchase:<orderId>'))` (same mechanism as checkout fulfilment and the Medusa sync; the key is the ORDER, identical for the three paths), RE-READS the order, its `FulfillmentLog` and its engine jobs INSIDE the lock (`lib/fulfillment/supplier-purchase-decision.ts`, pure), and — only if nothing proves a purchase and nobody holds the claim — writes the durable claim `FulfillmentLog.status = BUYING`. The supplier call happens AFTER the commit, never inside a transaction. Evidence of a purchase = `Order.supplierOrderId`, a BOUGHT log, or an engine `SupplierFulfillmentOrder` carrying a supplier order id (not FAILED/CANCELLED) **for that order only**: a job groups every AliExpress order of a cart but the adapter buys its FIRST line only, so a job proves a purchase for its first line (smallest `SupplierFulfillmentOrderLine.id`) and for no other order — the cart's second order stays purchasable and is never stamped with the first one's AliExpress id. No schema change. Every write that does not hold the claim is conditional (`updateMany` on the status it read): a stale read can no longer erase a claim another path took.
- **What an answer means is an ALLOW-LIST, not a deny-list** (`classifyPlaceOrderAnswer`, `lib/aliexpress-ds-create-order.ts`). Only an explicit, RECOGNISED business refusal (address, stock/inventory, price, SKU, product offline, shipping, `A00*`) or a dead token is **definitive**; a gateway rejection of the CALL itself (unknown method, no permission, bad signature/timestamp) lets the next method try; a throttle backs off. **Everything else is UNCERTAIN**: timeouts (`timed out` and `timeout`), network errors, unreadable or non-2xx answers (`strictHttpStatus`), gateway/ISP/ISV errors whose text is not on the list ("Remote service error"…), a 2xx without order id and without a recognised refusal — and a fault message that merely contains a business word is still uncertain. An uncertain answer is **never sent again** to another host/method (the AE payload has no idempotency key, so only this classification protects), the `BUYING` claim is kept, auto-buy skips its browser fallback and retry, the order.paid workers never retry it (`isNeverRetryFulfillError`, by prefix — whatever the text says), an alert goes out (Sentry `SUPPLIER_PURCHASE_IN_DOUBT:*` **and the ops webhook**) and the order is flagged `MANUAL_REQUIRED`. A claim NEVER expires into a new purchase (older than 15 min it is only reported `stale`). If the purchase succeeded but could not be written down (`placed_but_unrecorded`) the AliExpress id is in the alert — it is stored nowhere else. **What this guarantees**: no second purchase through any path that uses the gate, for any answer not on the allow-list; a refusal text missing from the list fails SAFE (a human looks), never open. **What it does not**: a refusal AliExpress words in a way the list does not know is escalated to a human instead of being retried.
- **A claim orphaned by a crash cannot alert itself** (the process is dead): the existing `sentinel-scan` cron (every 30 min, no new cron) runs `collectPurchaseInDoubtSignals` — every `FulfillmentLog` in BUYING for more than 15 min becomes ONE P0 signal `fulfillment.purchase_in_doubt` on its order (idempotent, closes by itself), and a NEW P0 is pushed to the ops webhook by `runSentinelScan`. The BullMQ worker never initialises Sentry, which is why the alerts above also go through `opsWebhookAlert` (`SLACK_WEBHOOK_URL` / `DISCORD_WEBHOOK_URL`). The `order.paid` fast path reports a stale claim too.
- **Reconciling an order "in doubt" (human, after looking at the AliExpress order list)**: order EXISTS → set `Order.supplierOrderId` (every path then answers "already placed") and the log to BOUGHT with `aeOrderId`; order does NOT exist → set the `FulfillmentLog` to `FAILED` (that releases the claim; a retry may buy). Never delete the log. The admin "retry" (`retryAdminAutoBuyFulfillmentLog`) refuses a BUYING log (409 `purchase_in_doubt`) — it used to reset one older than 10 min to PENDING and buy again. **Refunding an order whose purchase is in doubt** (SLA cron, lost dispute, admin refund) does not cancel anything (there is no order id): `attemptExternalOrderCancellation` flags the log `MANUAL_REQUIRED` (`purchase_in_doubt`) and alerts, so the human also checks AliExpress for an order to cancel.
- **Margin floor before any purchase** (`lib/fulfillment/auto-buy-margin.ts`, pure, integer cents): `margin = HT line − supplier transfer − affiliate transfer − estimated Stripe fee (2.9 % + 25 c on the TTC charge) − AE cost (unit price × quantity + shipping, of the SKU actually bought)`; the transfers come from the existing settlement functions (`computeTransferAmountsFromOrder`), so the gate cannot disagree with the payouts (`auto-buy-margin.test.ts` checks it against the real checkout functions over 576 combinations). Refused — never bought — when the margin is below `AUTO_BUY_MIN_MARGIN_CENTS` (default **300**; only a plain integer ≥ 0 is accepted, anything else falls back to 300), when it is negative whatever the floor, or when the cost/revenue is unknown: **a price ≤ 0 or a shipping ≤ 0 is UNKNOWN** — `SupplierLink.aeShippingCents` is `NOT NULL DEFAULT 0` and every importer writes 0, so a stored 0 means "never entered", not "free"; enter a real (or deliberately conservative) amount on the link. The 100-cent placeholder `enlist-ae-product.ts` writes on a variant when the AE price is unknown cannot be told from a real 1.00 EUR price: replace it with the real price. A refusal is traced (`MARGIN_REFUSED:<reason>:margin=…:floor=…` on the log, appended to the order's errors), alerted (Sentry warning + ops webhook) and flags the order `MANUAL_REQUIRED`. **The gate itself neither retries nor refunds** — but it does not suspend the buyer protections: `enforce-supplier-ship-sla` still auto-cancels and refunds any paid order with no tracking past its deadline (10 days + 3 days of grace by default), margin-refused orders included, and notifies the supplier and the affiliate as for any SLA breach. That is unchanged on purpose; the owner has that window to decide.
- **Re-running a margin refusal**: admin "Retry" and the Sentinel `retry-auto-buy` playbook answer **409 `margin_refused` with the trace** and change nothing (they used to flip the log to PENDING, erase the trace and enqueue a job the queue silently ignored because a finished job keeps its id). Sentinel reports a refused margin as `fulfillment.margin_refused` (open the order), not as a retryable failure. After fixing the price or the floor, re-run through `POST /api/orders/<id>/fulfill` (admin session or cron secret), which re-evaluates the margin.
- **Finding to decide (not hidden)**: the supplier payout is `wholesale − commission − supplier fee` and the AE cost is deducted from NO payout, so on an auto-buy line Affisell keeps `supplier fee + affiliate fee` and pays the AE cost out of its own pocket. With the current fees most lines will be refused by the floor until the owner decides who bears the AE cost. The gate reports what the code really does; it does not assume the model is right.
- **Not covered**: the ops-only `POST /api/aliexpress/order/create` (no order id, secret-protected); lines 2..n of a multi-product AliExpress group in the engine (the adapter buys only the first line — an under-purchase, never a double one; the others are bought through `order.paid` / auto-buy, each under its own claim); a legacy multi-line engine job (bought before the gate) is attributed to its smallest-id line, an assumption that holds for jobs created in order; the engine/`order.paid` paths are still not behind `AUTO_BUY_ENABLED` (only `auto-buy.ts` is) — they are protected by the claim and the margin floor, not by the opt-in; `autoBuyCardAmountCents` ignores the quantity; a finished BullMQ auto-buy job keeps its id, so a "retry" of a FAILED log can still enqueue nothing (pre-existing). Tests: `supplier-purchase-decision`, `supplier-purchase-guard` (in-memory lock that really serialises), `supplier-purchase-paths` (the three real paths at once), `aliexpress-ds-create-order-uncertain`, `aliexpress-ds-sync-strict-http`, `order-paid-no-retry-uncertain`, `auto-buy-margin`, `auto-order-apply-place-result`, `auto-order-engine-circuit-gate`, `orders-fulfill-route-gate-status`, `retry-auto-buy-in-doubt`, `external-order-cancellation`, `sentinel/purchase-in-doubt`, `sentinel/run-scan-in-doubt`.

## Environment isolation, startup validation, backups (finalisation master K1 / J3 / J2)

- **`VERCEL_ENV` decides the environment, never `NODE_ENV`** (`production` on a Preview too): `lib/runtime-environment.ts` (`resolveRuntimeEnvironment`, `resolveSentryEnvironment`). Sentry's `environment` is `production` / `preview` / `development`, and `unknown` when there is no Vercel signal — never `production` without proof (the browser bundle reads `NEXT_PUBLIC_VERCEL_ENV`, inlined by `next.config.ts`; read it as a literal `process.env.NEXT_PUBLIC_VERCEL_ENV`, Next inlines nothing else).
- **Redis keys and BullMQ queues carry the environment**: every key goes through `redisKey()` and every `Queue` / `Worker` takes `prefix: bullmqPrefix()` (`lib/redis-namespace.ts`). **Production = the EMPTY namespace** (no existing key changed, BullMQ keeps its default `bull`), Preview = `preview:` / `preview:bull`, development `dev:`, tests `test:`. `lib/__tests__/redis-namespace.test.ts` inventories every Redis user and fails on a new one that forgets the namespace — a new Redis key MUST use `redisKey()`. **Trap**: a worker host outside Vercel resolves its namespace from its own environment; without `NODE_ENV=production` (or `AFFISELL_REDIS_NAMESPACE=production`) it listens on `dev:bull` and consumes nothing of production's queues. `AFFISELL_REDIS_NAMESPACE=production` is ignored on a Vercel Preview / Development deployment.
- **A LIVE Stripe key never runs outside production**: `lib/stripe.ts` → `assertStripeKeyAllowed` (`lib/stripe-key-guard.ts`) refuses `sk_live_` / `rk_live_` unless the runtime is production (`VERCEL_ENV=production`, or `NODE_ENV=production` off Vercel: the worker). The error and the log name the environment, never the key. `AFFISELL_ALLOW_LIVE_STRIPE_OUTSIDE_PRODUCTION=1` exists for a developer machine and is ignored on any Vercel deployment. `lib/stripe.ts` is the only `new Stripe(` in `lib/` / `app/` (a test fails on a second one).
- **A Preview never gets a client on the production database**: `assertPreviewNotOnProductionDatabase` (`lib/db-env.ts`) runs before the default, fulfilment and Radar Prisma clients are created (`lib/prisma.ts`, `lib/prisma-radar.ts`, including `RADAR_DATABASE_URL` / `MARKET_INTELLI_DATABASE_URL`). Log tag `[env-guard]`; masked endpoint only. A Radar database that is not a Neon production host cannot be recognised by name: keep those variables absent or staging on Preview.
- **Startup validation** (`lib/env-validation.ts`, called from `instrumentation.ts`): one `[env-validation]` line per server process, variable NAMES and static messages only (a test plants sentinel values and fails if one leaks), nothing during `next build`, never throws. Production critical: `AUTH_SECRET|NEXTAUTH_SECRET`, `DATABASE_URL`, `CRON_SECRET`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `ENCRYPTION_KEY|TIKTOK_TOKEN_ENCRYPTION_KEY`; it also flags a Preview on the production database, a live Stripe key outside production, a `CRON_SECRET` reused as another secret, and an enabled `AUTO_BUY_ENABLED`. Add a requirement to `ENV_REQUIREMENTS` when you add a variable a deployment cannot work without. The proxy logs `[proxy] auth_secret_missing_on_request` (ERROR, ≤ 1/min/instance) when it has no session secret; the guards still treat the visitor as anonymous.
- **Operations**: per-environment variable matrix, Stripe events, Replicate signing secret, Neon / Redis / Sentry / alert settings — `docs/EXTERNAL-OPS-RUNBOOK.md` (nothing in it has been executed; every action needs the founder's authorisation). Backup / PITR restore / Redis / Blob-R2 — `docs/BACKUP-RESTORE.md` (a written procedure, **never exercised**: its checklist §9 has not been run). Restore a Neon branch **in place** (same `ep-misty-sea-…` endpoint): a restore to a new branch gets an endpoint that the repo's production guards no longer recognise.
- **`vitest` in a Git worktree with a symlinked `node_modules`**: `@prisma/client` resolves the real path and loads the MAIN checkout's `.env` into the test process (measured on 2026-11-13, names only: Stripe, encryption and a few test-account variables; no database, Redis or KV URL was among them); `vitest-env/no-real-datastores.ts` only looks at the working directory. `vitest-env-isolation.test.ts` then fails (2 tests) — an artefact of that setup (nothing in K1/J3 touches it), not a regression. Remember that a `STRIPE_SECRET_KEY` leaked this way would be refused by the live-key guard in a test.
