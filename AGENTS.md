## Client components vs Prisma

- `"use client"` modules must **not** value-import `@/lib/*` files that import `@/lib/prisma` (use `*-types.ts`, `*-shared.ts`, or `import type` only).
- Run `npm run check:client-prisma` before push when touching dashboard/nav/home client UI.

## Local dev (port 3001)

- `npm run dev` → `scripts/next-dev-port.mjs` (default **3001**, next free port if busy).
- Copy `.env.local.example` → `.env.local`: align `PORT`, `NEXT_PUBLIC_APP_URL`, `NEXTAUTH_URL`.
- Helpers: `lib/dev-localhost-url.ts`, `scripts/dev-localhost-url.mjs`; `npm run dev:url` / `dev:open:wizard-v2`.
- **Zsh:** quote `?query` URLs or use npm open scripts — unquoted `?wizard=v2` triggers glob errors.
- **`Can't reach database server at …:5432` in `next dev`** = this machine can not open a Postgres connection: run `node scripts/dev-db-preflight.mjs` (host only, never credentials; bare TCP, no query). It tells apart a network that blocks port 5432 while HTTPS works (company / hotel Wi-Fi, VPN, firewall → change network), no internet, and Neon unavailable.
- Wizard v2: `npm run verify:wizard-v2:dev` (env preflight) · `npm run test:wizard:v2` (preflight + unit tests).

## Merchant custom domains & storefront theme

- **DNS**: merchants set `CNAME` → `STORE_CNAME_TARGET` (default `cname.affisell.com`), then **Activate domain + SSL** in Store profile (`/dashboard/*/settings/store`) — or wait for cron auto-activation.
- **Auto subdomain**: on signup, `{slug}.{AFFISELL_STORE_HOST_SUFFIX}` (default `shops.affisell.com`) — same catalog as `/shops/{slug}`; wildcard DNS on Vercel required in prod.
- **Subdomain HTTPS is decided by a real TLS handshake, not by Vercel's flag** (`lib/store-subdomain-reachability.ts`, applied in `lib/store-subdomain-provisioning.ts` and the 30-min cron). `Store.subdomainVercelStatus` can be `unreachable` = Vercel says configured but a browser cannot open it; the public URL then stays on `/shops/{slug}` and recovers by itself once the handshake works. A network blip (timeout/reset) never flips a status. Probe runs in production only (`AFFISELL_SUBDOMAIN_PROBE=0|1` to force). Diagnose: `npm run verify:store-domains` (add `-- <slug>` for one store).
- **Known infra constraint (Cloudflare)**: Cloudflare's free Universal SSL covers `affisell.com` and `*.affisell.com` only — **not** `{slug}.shops.affisell.com` (two labels) → `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`. Fix: order an Advanced Certificate for `shops.affisell.com` + `*.shops.affisell.com` (SSL mode "Full"), or set the `*.shops` DNS record to DNS-only → `cname.vercel-dns.com` (Vercel then certifies each store host).
- **Routing**: `middleware` calls `/api/store/resolve-host` and rewrites verified hosts to `/shops/:slug` (affiliate) or `/store/supplier/:slug` (supplier). Dashboard/checkout paths redirect to the platform origin.
- **Vercel SSL (1-click)**: `VERCEL_API_TOKEN` + `VERCEL_PROJECT_ID` → `POST /api/store/verify-domain` registers hostname + www redirect on the Affisell Vercel project. Cron `GET /api/cron/sync-store-vercel-domains` (every 30 min via GitHub Actions) auto-verifies DNS + retries pending SSL. Preflight: `npm run verify:store-domains`.
- **Theme**: `Store.storefrontTheme` JSON (`primary`, `accent` hex) — **Brand Studio** (`/dashboard/affiliate/brand-studio`, `/dashboard/supplier/storefront`); applied via `StorefrontThemeStyles` on public shops.
- **Status**: `Store.vercelDomainStatus` (`active` | `pending` | `failed` | `skipped`); polled in UI via `GET /api/store/domain-status`.
- **Smart header** (live `/shops/{slug}` only — `StorefrontBuyerChrome smartHeader`, Brand Studio preview keeps the plain header): `position: sticky` can't work there (the header's container is as tall as the header; mobile html/body are `overflow-x: hidden`), so the header is `fixed` + an in-flow spacer of the same height (zero layout shift). Away while reading down, back as a compact bar (trust rail folded via `[data-chrome-rail]` in `globals.css`) on the way up, full again near the top; stays visible while the menu is open or focus is inside it; `prefers-reduced-motion` keeps the static header. Mobile-browser hardening: scroll offsets past the real end of the page (iOS rubber-band) and scroll shifts that follow a viewport resize (iOS toolbar collapse, rotation) are never read as a scroll direction. Pure logic + tests: `lib/storefront/header-mode.ts`; hooks: `hooks/use-header-mode.ts`.

## Listing readiness — product safety (GPSR) & identity

- **One definition of "ready to publish"** for a physical product: `lib/listing-compliance/evaluate.ts` (pure, shared by the API and the forms). Checks PRESENCE/FORMAT of the declared data, never its truth: manufacturer name / address / email / country, an **EU responsible person when the manufacturer is outside the EU**, GTIN check digit; brand and missing GTIN are advisory only. Digital goods are out of scope.
- **Rollout switch `LISTING_READINESS_MODE`** = `off` | `warn` (**default**) | `enforce`, read per request (flip it on Vercel, no code deploy). `warn` only logs `[listing-readiness]` lines (what WOULD be refused); `enforce` answers **422 `listing_not_ready`** with language-neutral codes, before anything is written. It applies to **new publications only** (create live, draft → live, CSV rows): drafts and edits of listings that are already live are never blocked, so legacy listings stay editable. Wired in `POST /api/supplier/products`, `PUT /api/supplier/products/[id]`, `POST /api/supplier/bulk-import/commit` and the legacy quick-upload `POST /api/products/upload` (helper `lib/listing-compliance/gate.server.ts`, never throws).
- **Before flipping to `enforce`**: run `npm run report:listing-readiness` (READ-ONLY; uses the DATABASE_URL of `.env.local` — possibly production; `--target` first, `--confirm-endpoint=<ep>` required on production — see « Read-only reports » below) and watch the `[listing-readiness] result: would_refuse_if_enforced` logs. Every UI that publishes can comply: classic form, guided wizard and Express wizard (`ListingComplianceSection`; Express opens it on a 422), CSV template columns (`manufacturer_*`, `eu_rep_*`, `gtin`). **Automated imports go through the same gate since 2026-11-18** (`decideImportPublication`, `lib/listing-compliance/import-publication.server.ts`): store sync (Shopify / WooCommerce), `supplier-products-import-exec`, Dropforge and the marketplace URL import publish only through it; in `enforce` an incomplete import is CREATED AS A DRAFT instead of being refused (an import is a batch), and the URL-import publish answers `listing_not_ready` (422). A re-import never unpublishes. The store sync no longer unpublishes out-of-stock products nor rewrites publication / commission on later syncs (lifecycle rules). Still outside the gate: the admin AliExpress enlist (`enlist-ae-product.ts`, explicit admin publish = Affisell validation) and the reseller URL import, which since 2026-11-18 is **import → validation → publication** (`lib/reseller-import/review.ts` pure + `.server.ts`): a NEW import is a DRAFT on the Import Vault account tagged `import-review:pending`, the reseller's listing is created UNLISTED and its wish to go live is recorded (`AuditLog` `reseller_import.submitted`, id `reseller-import-request:<listing>`); an ADMIN decides with `GET /api/admin/reseller-imports` and `POST /api/admin/reseller-imports/<productId>/review` `{decision: approve|reject, note}`. **Review, compliance and publication are three separate things** (`importPublicationStatus`, founder rule 2026-11-18): approve records the REVIEW; the product is published and the requested listings listed ONLY when its blocking product-safety data is complete, judged STRICTLY whatever `LISTING_READINESS_MODE` says (observation mode never lets an Affisell-validated product with a blocking defect become sellable) — otherwise it stays a draft (`published: false` + the codes) in the « approved — not publishable » list, the admin completes the data (`PUT …/<productId>/compliance`, reserved compliance keys only, refused on a live product, AuditLog `reseller_import.compliance_updated` with keys only) and publishes explicitly (`POST …/<productId>/publish` `{note}`, compliance re-judged, AuditLog `reseller_import.published`); approving a legacy product ALREADY live changes nothing to its publication (founder decision); reject = draft + every listing unlisted; each decision is an `AuditLog` `reseller_import.reviewed`. A re-import never changes a decision. A reseller can not list an unreviewed product by hand: `PATCH /api/affiliate/listings/[id]` and `PATCH /api/affiliate/products/[id]` → 409 `product_not_reviewed`, `PATCH /api/affiliate/products/bulk` skips those listings and answers `notReviewed: n` (`mayListOnProduct`, fail-closed when the product is unreadable); the import result screen tells the reseller « en attente de validation » (`importPage.jobToastPendingReview`, 8 locales). **Imports made before 2026-11-18 (no tag) keep their state** and appear as `legacy_unreviewed` in the admin list: pulling them is a founder decision. Admin page `/admin/reseller-imports` (nav « Imports revendeurs »): list by state (to validate / legacy / rejected), detail for VERIFYING (`GET /api/admin/reseller-imports/<productId>`, `loadResellerImportDetail`: photos, price, stock, source host, description excerpt, product-safety gate result, every listing with its reseller name — never an e-mail — and whether it asked to go live, past decisions), then approve / reject with a mandatory reason (reject asks for a second click and says how many live listings will be withdrawn). The page shows the three notions side by side (review / compliance / publication), embeds the compliance editor for a non-live import and a « Publier » button. Tests: `import-publication-gate`, `supplier-sync-lifecycle`.
- **Storage = `ProductAttribute` rows with reserved keys** (`lib/listing-compliance/keys.ts`: `brand`, `ean`, `mpn`, `gtin_exempt`, `gpsr_*`), **not new columns on `Product`**: the migration used to be warn-only in the Vercel build (today it is applied by hand BEFORE the push and the build only verifies, see « Migrations » below), so a column on the hottest table could reach production code before the database has it. The only new table, `SupplierComplianceProfile` (the supplier's reusable manufacturer / EU-rep defaults), is isolated and accessed defensively (`profile.server.ts`: a missing table = "no profile", never a crash).
- **The profile is a default to OFFER, never applied silently**: a dropshipper is rarely the manufacturer, so each product still carries — and the supplier still confirms — its own values (one-click prefill buttons in `GpsrFields`). Settings page: `/dashboard/supplier/settings/compliance`.
- **`managedAttributeKeys`**: `PUT /api/supplier/products/[id]` replaces the whole attribute set with what the form sends; a form only knows its category's attributes, so saving used to delete everything else (guided-wizard manufacturer / material / dimensions). A form now declares the keys it owns and the rest is preserved (`mergeManagedProductAttributes`). Without the declaration the legacy contract is unchanged.
- **Buyer-facing labels are translated from the KEY** (`productSpecs.keys.*`, `lib/listing-compliance/spec-labels.ts`): rows were stored with the French label the wizard wrote. Regulatory rows are excluded from product highlights (`highlight: false`).
- **Duplicates** (`GET /api/supplier/products/duplicate-check`): the supplier's OTHER products with the same GTIN, main photo or name — advisory only; other suppliers' products are never considered.
- **Hydration**: the country `<select>` is filled only after hydration (`useHydrated`): ICU country names/sort order differ between Node and the browser and caused a React hydration mismatch.

## Supplier add-product — earnings preview, photos, drafts (guided wizard)

- **What a supplier really receives** (`lib/supplier-earning-preview.ts`): `price − round(price × commission%) − round(price × feeBps / 10 000)`, i.e. the reseller's commission is paid OUT OF the supplier's price and Affisell's category fee comes on top (catalogue channel; auto-buy adds a surcharge and uses the AliExpress wholesale — not modelled). `lib/__tests__/supplier-earning-preview.test.ts` compares it with the real settlement functions (`computeMarketplaceOrderSettlement`, `buildPhase1FeesForOrderLine`, `netSupplierPayoutCents`) over 700 price/commission/fee combinations: if you change settlement, that test must keep passing. The classic form's "Simulation live" card used to show the full catalogue price as "Vous recevez / vente" — now it shows the net, and "(avant frais Affisell)" while the category is unknown.
- **Fee rate**: `GET /api/supplier/category-affisell-commission` now also returns `supplierCatalogFeeBps` — the rate THIS supplier pays (a negotiated `User.supplierFeeBps` / `supplierFeeBpsCatalog` wins over the category grid, same resolution as at settlement). Client hook: `useSupplierFeeBps` (`null` while unknown → the UI never invents a rate).
- **Guided wizard photos**: up to `GUIDED_MAX_PHOTOS` (8), main photo first (make-main / remove / promote-next), photo-quality hint reused from the classic form (`SupplierPhotoQualityHint`). A picked `FileList` is copied before the input is cleared (it is live in Safari/Firefox).
- **Guided wizard local draft** (`lib/supplier-guided-draft.ts`): autosaved to localStorage (800 ms debounce) under `affisell:guided-add-draft:v1:<supplierId>`, offered back on the next opening ("Resume / Start over") — NEVER restored silently, and the stored draft is not overwritten by the empty form while the offer is pending. Everything read back is re-sanitised (https photo URLs only, whitelisted attribute keys, category checked against the wizard's list, numbers as numbers); scoped to the supplier id; expires after 7 days; cleared on publish, on a server draft save and on "Start over".
- **Shipping is included in the supplier's price — buyers are never charged shipping.** Checkout (`lib/marketplace-checkout.ts`) carries product lines only and the settlement has no shipping term, so a "shipping cost" or "free-shipping threshold" a supplier typed in was never paid by anyone. Hence: no shipping-cost input in the classic form, no `shipping_cost_eur` column in the CSV template (an old file that still has a non-zero value parses, stores nothing and gets a `shippingCostIgnored` warning), no "Free shipping over €X" on the PDP, and `SupplierShippingIncludedNotice` (`components/supplier/shipping-included-notice.tsx`, `supplier.shippingIncluded.*` in 8 locales) under every price field telling suppliers to build their delivery cost into the price. The `Product.shippingCost` / `freeShippingThreshold` columns, the API parser (`lib/supplier-product-shipping.ts`) and stored values are untouched (no migration; PUT leaves them alone because forms no longer send them). The `freeShipping` flag stays as a badge + marketplace filter only (it does not change what a buyer pays). **If buyer-paid shipping is ever introduced** (Stripe `shipping_options`, VAT on shipping, supplier share, refunds), that is a money-path project that needs the accountant first — revisit these fields then.
- **Per-product return window (supplier decides, supplier pays — owner decision 2026-10-07)** (`lib/return-terms.ts`, `lib/return-terms.server.ts`): a supplier can offer 30/60/90 days (any whole number 15–90 via API) instead of the legal 14 — **extension only, never shorter**. Stored as the reserved `ProductAttribute` `return_window_days` (no row = 14 days; sanitised in `normalizeProductAttributesFromBody` for every route; kept by PUT's `alwaysKeep`; hidden from spec rows via `HIDDEN_SPEC_KEYS`). **Frozen at purchase** in the isolated table `OrderReturnTerms` (migration `20261007120000_order_return_terms`; one row per order, only written for an extension) by `recordOrderReturnTerms`, called from `scheduleMerchantOrderAlerts` AFTER the response — never inside the payment transaction, idempotent, never throws, only for orders created in the last hour — so shortening the window later never touches orders already placed. Readers (`return` route, buyer order list/detail) use `loadOrderReturnWindowDays*`, which fall back to the legal 14 days when the table is missing (apply the migration by hand: `DATABASE_URL='<url>' npm run schema:migrate -- --expect-endpoint <ep-id>`). The refund path is unchanged: the supplier approves the case and the refund is taken from their share (`supplierReturnLiabilityCents`) exactly like a legal-window return. Return shipping cost is NOT modelled (the buyer ships back with tracking, as before), so the page says "Returns accepted within N days", never "free returns". Form: `ReturnWindowField` in the classic form, the guided wizard (details step, kept in its local draft) and the Express wizard (product-safety section) since 2026-11-18 — all three write the same reserved row; the PDP chip appears only for an extension. A category change in the classic form now keeps product-level values (identity, GPSR, return window) instead of wiping them.
- **Warranty — still a gap**: per-SKU `warrantyMonths` (advanced SKU table; `lib/product-warranty.ts`) feeds a badge the reseller can switch on (`showWarranty`), but the return flow stops at the return window, so a buyer has NO on-platform way to claim a warranty after it (reason `DEFECTIVE_OR_BROKEN` only works inside it). Showing "2-year warranty" therefore promises more than the platform can process; a warranty-claim path (same snapshot table + a claim reason accepted until `warrantyMonths`) is the follow-up, not built.

## Reseller selling-price history and profitability attribution (commercial intelligence)

- **Every change of a reseller's selling price is recorded by the DATABASE** (migration `20261117090000_listing_price_history`, trigger `AffiliateProduct_listing_price_history` → table `ListingPriceHistory`): `sellingPriceCents` (variantKey NULL) and each `variantPricing.<key>.sellingPriceCents` (`opt:<key>`; a removed override is a row with `priceCents` NULL). Whatever writes (UI, API, imports, crons, seeds, scripts), a row is written only on a real change; old/new price, `effectiveAt`, `currency` (EUR), `affiliateId`, `productId`. No foreign key and the trigger never fails the observed write; CHECK constraints only guard what it writes. **Apply by hand before the push that ships it** (`schema:migrate`); until then readers see "no history" (defensive reads).
- **Source / actor**: a writer declares them for its transaction with `updateListingWithPriceSource` / `upsertListingWithPriceSource` / `declareListingPriceSource` (`lib/listing-price-history/record.server.ts`: `set_config(…, true)` + the write in ONE transaction). Sources: `lib/listing-price-history/sources.ts`. Wired: listing editor + listings API (`reseller_ui`), listing creation (`listing_create`), margin auto-fix (`margin_auto_fix`), variant auto-adjust cron (`auto_adjust`). Any other writer is still recorded, as `unattributed` — when you add a writer of these columns, declare its source.
- **Reads are scoped by reseller**: `GET /api/affiliate/listings/:id/price-history` (owner only, 404 otherwise, never exposes `actorId`), `loadListingPriceChanges(affiliateId, …)`.
- **Net earnings use what the order TRANSFERS** (`netAffiliateTransferCents`: commission + markup − Affisell's fee), never `Order.affiliatePayoutCents` alone (the commission). Refunds reverse it pro rata like `reverseConnectTransfersForRefund`.
- **Why profitability moved** (`lib/intelligence/profit-attribution.ts`): exact split of Δnet between volume, selling price, supplier price, commission, fees and refunds from the ORDER snapshots, plus a residual that is shown, never attributed. "You lowered your price" only when `ListingPriceHistory` shows a cut; otherwise "lower price collected". **Simulations** (`lib/intelligence/price-simulation.ts`) are labelled as calculations, need ≥ 5 orders in 30 days, and never change a price.

## Reseller copilot — real net per sale and a ready-to-sell selection (innovation cycle 2026-11-19)

- **What a reseller is really paid per sale** (`lib/reseller-copilot/net-per-sale.ts`, pure, client-safe): commission (`round(supplier price × commission%)`) + markup (`selling HT − supplier price`, 0 below it) − Affisell's reseller fee (`round(gross × User.affiliatePlatformFeeBps / 10 000)`, default 20 % when the reseller has none — `feeIsDefault`). `reseller-copilot.test.ts` compares it with the REAL settlement (`computeMarketplaceOrderSettlement` + `computePhase1OrderFees` + `netAffiliateTransferCents`) over 1 260 combinations: if you change settlement, that test must keep passing. The catalogue cards (`buildAffiliateCatalogCardEconomics` → `netPartnerGainCents`, `affisellFeeCents`, `feeBps`) now show the NET with its breakdown and « prix hors taxes »; `totalPartnerGainCents` stays the gross (it used to be shown alone as the reseller's revenue). The catalogue page passes the reseller's own fee rate. The buyer's TTC price is an ESTIMATE (20 %; Stripe Tax decides).
- **Selection** (`lib/reseller-copilot/selection.ts` pure + `.server.ts`, `GET|POST /api/affiliate/copilot/selection` — AFFILIATE, rate-limited, POST same-site; panel `ResellerCopilotPanel` on `/dashboard/affiliate/catalog`, `affiliate.copilot.*` 8 locales): the reseller's catalogue (same visibility as `buildAffiliateCatalogProductWhere`, ≤ 300 newest, products already in the shop left out), each product with its real net at the suggested price (supplier + 30 %, as the quick add), readiness (`bloque`: no explicit commission — a sale would become an unallocated line —, out of stock, awaiting Affisell review, no supplier price; `a_verifier`: stock unknown (variants only in the table), ≤ 3 units, net < 2 €; else `pret`), observed demand (paid orders 30 days, resellers listing). Ready first, highest net, then demand; blocked returned apart with reasons. Every reason is qualified `catalogue` / `calcul` / `observe` — no forecast. **Rising on Affisell** (innovation portfolio A, 2026-11-19): a candidate whose paid orders accelerate clearly more than the marketplace — the cockpit's OWN `detectEmerging` test (exact binomial vs the marketplace's growth, Bonferroni over the candidates, size floors), one definition — AND sold by ≥ 2 resellers (`RISING_MIN_SELLING_RESELLERS`: one reseller's own campaign is not a trend) AND spread over ≥ 3 distinct days in the 14-day window (`RISING_MIN_DISTINCT_DAYS`: one bulk day is a one-off) gets `trend.rising` + reason `rising_on_affisell` (`observe`). **Popularity never replaces profitability**: it lifts a product within its readiness ONLY when its net per sale ≥ the median net of the selectable products (`risingLifts`), otherwise the badge stays and the place is by net; the card shows the comparison (14 days vs the 42 before) and the signal's nature (`risingNature`); **Personalised by the reseller's REAL categories** (founder brief 2026-11-19, `loadMyCategories`: categories of its live listings + of its paid orders over 90 days — its own activity only; none = no personalisation): each item gets `fit` `your_categories` / `discovery` (reason `in_your_categories` / `discovery`, `observe`); for ORDERING ONLY an in-category net counts × (1 + `CATEGORY_AFFINITY_TOLERANCE` 0.15) — it never passes a product paying more than 15 % more, the shown figures never change — and `DISCOVERY_SHARE` (25 %) of the picks stay in other categories when there are any (lowest in-category picks replaced), so the reseller is never locked in its habits; card chips `affiliate.copilot.fit.*` + `personalisedNote`. badge « En forte progression sur Affisell » (`affiliate.copilot.rising`). Counts only, no reseller / supplier named; a failed read = no trend, never a blocked selection. Adding (≤ 20) RE-ASSESSES each product and goes through the existing `quickAddAffiliateListing` (same rules / publication gates); nothing else is written. Doc: `docs/INNOVATION-CYCLE-2026-11.md`. Tests: `reseller-copilot`.

- **FX → costs: what is verified vs hypothesised.** Verified: AliExpress costs are stored in EUR once, at import / enlist (`SupplierLink.aePriceCents`), and nothing refreshes them on a schedule (the `aliexpress-refresh` cron renews the API TOKEN, not prices); Affisell pays AliExpress in EUR. Hypothesis: that AliExpress's euro price follows the exchange rate (sellers pricing in USD / CNY). So the FX signal is `kind: hypothesis`: the title states only the rate move, the cost effect is an evidence line labelled « Hypothèse », `important` only when active links have a stored cost older than the comparison base date (`SupplierLink.updatedAt`), else `study`, and the action is "re-check the stored costs" — never "your costs rose by X".

Before this, a `currency_code: "USD"` SKU was stored as euros.
- **Dispute activity** (`disputeActivitySignal`): Stripe's definition (docs.stripe.com/disputes/measuring) — disputes by the date they were OPENED over successful payments of the same period. **The 0.75 % is Stripe's "excessive" reference for the account, NOT a card-network fine threshold**: Visa VAMP / Mastercard ECM work per calendar month with their own ratios and minimum counts (ECM ≥ 100 chargebacks; VAMP also counts early fraud warnings, which Affisell does not record), so at Affisell's volume they can not trigger; the exposure is Stripe's review of the platform account. Computed on 30 rolling days over distinct CHECKOUT payments (a cart's orders are `<session>:line:<i>` — counting orders would understate the activity), distinct `dp_` ids of the dispute ledger. `critical` needs ≥ 3 disputes (one dispute on 60 payments is already "above 0.75 %"); below that `important`, low confidence. The Stripe dashboard (Analytics) is the reference.
- **No false alarms by construction** (`detectors.ts`): category demand is corrected for MULTIPLE TESTING (`zThresholdForTests`: Bonferroni, 5 % family-wise — 100 categories at 2σ each would raise ≈ 5 fake changes per run) and compared with the MARKETPLACE trend (a marketplace-wide move is ONE `market:marketplace:*` signal, not one per category); ≥ 10 orders to be judged; a capped order read (`MAX_ORDERS`, newest first) is never compared (`echantillon_tronque`). Signal ids are stable per object (and per day for daily facts) and `rankSignals` dedupes them.
- **Access**: ADMIN only, enforced by the admin layout AND by the page itself; the only other importer of the collector is the ADMIN decision route (it returns the new decision's id, never the cockpit). Pinned by `admin-intelligence-access.test.ts`.

- **One table, two classes that must never be mixed** (`lib/events/names.ts`, the registry of every accepted event): **behavioral** (analytics: impression, click, view, search, cart, attribution touch) is recorded ONLY with the visitor's analytics consent and may carry `anonymousId`/`sessionId`/`channel`; **transactional** (the business journal: purchase, refund, return, delivery, review, creator listing add/remove) exists whatever the cookie choices are and NEVER carries a visitor identifier, a channel or a behavioral duration. `lib/events/row.ts` (`buildEventRow`, pure) enforces it; the `event_spine` migration repeats it as CHECK constraints, so a future code path that forgets still cannot store a visitor id on a business row.
- **Writer**: `recordEvents(events, { analyticsConsent })` (`lib/events/record.server.ts`) — idempotent (`eventId` unique + `createMany({ skipDuplicates })`; client UUID for behavioral, deterministic business key such as `purchase:{orderId}` for transactional), chunked, and it **never throws** (a failed analytics/journal write must not break the request). A database that is not migrated yet is logged once as `[events] schema_drift` — fix it by applying the migration (`npm run schema:migrate`, never a bare `prisma migrate deploy`), do not hide it.
- **Data minimisation lives in `lib/events/sanitize.ts` + `properties.ts`**: `properties` is NOT free-form (explicit allowed keys per event, one sanitizer per key); the search `query` is the only free text kept, and only as PRODUCT VOCABULARY — a query shaped like an e-mail, URL, phone/card/IBAN number, 5+ digit number (postal code, order number), identifier-like token (12+ chars mixing letters and digits), or street address is dropped WHOLE (fail closed, never half-masked), as is one over 8 words / 100 characters (valid GTINs are kept); person NAMES are not filtered on purpose (indistinguishable from brands — `lib/__tests__/events-search-query.test.ts` pins this limit); free-text or speculative keys (`variant`, `experiment_id`, `campaign_id`, `utm_term`) are not accepted at all and an inventory test fails when a key is added; referrers keep the HOST only; UTM values containing `@` are dropped; click identifiers (gclid/fbclid/ttclid) are never stored, only the platform. A browser can only send `clientEmittable` behavioral events and only via the strict schema in `lib/events/schema.ts` (no userId/creatorId/orderId/country/channel fields: the server derives them). Channel = deterministic rules in `lib/events/channel.ts` (no score).
- **Not wired yet**: nothing in the app calls the writer — the carousel / Pulse / agent checkout still use their legacy writes, and the 7 legacy readers (`eventType = 'view'` …) and `AffiliateProduct.clicks` are untouched. Wiring (ingestion endpoint, server emitters, attribution, `OrderAttribution`) is steps S2–S6, each to be validated by the owner.
- **Migrations**: explicit Prisma migration only — no runtime DDL, no `IF NOT EXISTS` to mask drift (`lib/__tests__/events-migration.test.ts` fails on it and on any schema/SQL mismatch). **Trap**: `prisma.config.ts` loads `.env.local` with `override: true`, so `DATABASE_URL="<branch>" npx prisma migrate deploy`, `npm run db:migrate` and `npm run migrate:deploy` really target the DEFAULT database, possibly production — never use them. **Deploy a schema with `DATABASE_URL='<url>' npm run schema:migrate -- --expect-endpoint <ep-id> [--confirm-production]` — by hand, locally, BEFORE the push (it refuses to run under Vercel)** and check it with `npm run schema:verify` (`scripts/schema-deploy.mjs`): explicit URL only (`.env*` is never read), `DATABASE_URL` / `DIRECT_URL` / `DATABASE_URL_UNPOOLED` must name the SAME endpoint, Prisma's own output must name it BEFORE anything is written, then `migrate deploy`, then the CATALOG is checked (`verify-event-spine` — `migrate status` alone proves nothing on a database that went through the old self-healing pipeline). **Every failure is a non-zero exit** (2 refused · 3 wrong target · 4 migration failed/unreadable · 5 verification failed). `scripts/prisma-explicit-db.mjs` is the low-level runner: `status`, `deploy`, and `resolve --rolled-back <name>` for a FAILED migration (P3009) — there is deliberately NO `--applied`, and a test fails if any file writes `_prisma_migrations` or runs `resolve --applied`. `prisma migrate diff` against this database also lists Medusa's tables as "to drop": never apply a diff or `db push`/`migrate dev` here. **Order**: migration in production → `schema:verify` → only then push the code (a push without that step is safe but fails: the Vercel build only VERIFIES and STOPS if the schema is missing — see below). `db:unlock` is a manual diagnostic (read-only by default; `--terminate --pid <n>` only for a stale session holding nothing but Prisma's migration lock `72707369`): it used to run before every build and killed any session holding any advisory lock, including the application's `pg_advisory_xact_lock` in payment / fulfilment / Medusa-sync transactions. Why the order matters (the legacy writers' `INSERT … RETURNING` lists all 22 columns), the pipeline, failure handling and the exact procedure: `docs/DEPLOY-SCHEMA-CHANGES.md`.
- **A developer machine never writes to PRODUCTION by accident** (S1.6.1). `.env` / `.env.local` hold the production URL and `@prisma/client` loads `.env` by itself, so a laptop-launched tool used to act on production silently (a unit test wrote fake AliExpress tokens into `PlatformOAuthCredential`). Vitest never sees `.env` (`vitest-env/no-real-datastores.ts`). `status` / `schema:verify` / `verify:event-spine` run in a server-enforced read-only session. Details: `docs/DEPLOY-SCHEMA-CHANGES.md` §10.
- **`next build` never writes to a database, and a local/CI `npm run build` cannot reach one.** `lib/build-write-guard.ts` is the outermost extension of every Prisma client (`lib/prisma.ts`, `lib/prisma-radar.ts`; a test fails if any other file creates a client): while Next reports `phase-production-build` (`isNextProductionBuildPhase()`), only known reads pass — create/update/delete, `$executeRaw*` and non-read-only `$queryRaw*` throw `BuildPhaseWriteBlockedError` BEFORE any connection; no override, and it does not depend on `VERCEL` / `VERCEL_ENV`. `npm run build` goes through `scripts/build-isolated.mjs`: on a real Vercel builder (`VERCEL=1` and NO secret `.env*` file in the working directory) nothing changes; elsewhere — including `vercel build` run on a laptop, which also sets `VERCEL=1` — every database/Redis credential (by name or by value shape, including those Next would load from `.env*`) and `SENTRY_AUTH_TOKEN` is set to an empty string for `next build` (Next never overrides a defined variable). `AFFISELL_BUILD_ALLOW_DB=1` keeps a NON-production database and refuses if any production URL is present. Next.js telemetry is off by default (`NEXT_TELEMETRY_DISABLED=1`). **Vercel pipeline (`scripts/vercel-build.mjs`, S1.6.1)**: `prisma generate` → `schema-deploy.mjs verify` (READ-ONLY: the database session itself is `default_transaction_read_only=on`) → `check:client-prisma` → `npm run build`, and it STOPS at the first failing step. **The Vercel build never migrates**: `BUILD_RUN_MIGRATIONS` is gone (not read, not in `vercel.json`) and `schema-deploy.mjs migrate` refuses to run in any Vercel context. Migrating is a separate step done by hand BEFORE the push (`schema:migrate -- --expect-endpoint <ep>`, staging for Previews too); a push whose migration was not applied fails at `verify` (exit 5) and the old code keeps serving. The build loads no `.env*`, runs no `db:unlock`, no repair SQL, nothing that marks a migration applied (`fix-p3009` / `deploy-repair.sql` and the cron's self-healing are gone; `/api/cron/migrate` is a read-only diagnostic). A Preview build whose database is not provably the staging branch (`ep-shy-wind-…`) is REFUSED; Production refuses staging/local; `VERCEL=1` on a developer machine is refused. ## Buyer identification — a typed identifier is not proof of ownership

- **Three entry points used to open a buyer session from an e-mail/phone alone**: `POST /api/auth/buyer-identify`, `POST /api/checkout/identified` (both via `lib/buyer-identify-session.ts`) and `POST /api/auth/post-checkout-buyer`. The last one trusted the e-mail on the Stripe session — which the PAYER types on Stripe's page (`lib/marketplace-checkout.ts` never presets `customer_email`) — so "it requires a paid session" was only a cost barrier, not a proof. A CUSTOMER session reaches `api/account/*` and `api/gdpr/*` (orders, returns, data export, account deletion).
- **Rule (`lib/buyer-account-ownership.server.ts`)**: a bare identifier never opens a session on an EXISTING account that has an owner (password, social login, verified e-mail) or history (orders, reward balance/ledger, reviews). A new or blank account keeps the one-step guest flow; a browser already signed in to that very account is let through. It fails closed (unreadable account = protected, database error = no session). In `post-checkout-buyer` the orders of the Stripe session being claimed are ignored, so a first-time guest who just paid still gets their session.
- **Refused buyers pay as guests**: `checkout/identified` runs `marketplaceCheckoutPOST` without `buyerUserId` (no reward redemption, nothing merged into the account); the order is still linked to the account by the e-mail Stripe collects. `buyer-identify` answers `requiresSignIn: true` with NO name and NO e-mail (the stored name must not leak) and the sheet shows `cart.identity.accountExists`; `post-checkout-buyer` answers 403 `sign_in_required` (the success page just skips the auto sign-in).
- **Known residual (Option A)**: a still-BLANK account (created, no order yet) can be claimed by whoever types its address first; the e-mail-proof flow (code by e-mail, `VerificationToken`) is the follow-up that closes it. The webhook still links an order paid with someone else's e-mail to that account (clutter, no data exposure). Tests: `buyer-account-ownership`, `buyer-identify-session`, `buyer-identify-routes`.

## Server-side fetch of user-chosen image URLs (SSRF)

- A listing's image URL is chosen by an affiliate or a supplier, and `GET /api/listing-card-image/[listingId]` is public: the server fetches it and hands it to `sharp`. **Never `fetch()` such a URL directly — use `fetchPublicImageBytes` (`lib/safe-remote-image.server.ts`).** `assertSafeOutboundUrl` alone only reads the hostname TEXT: `http://localtest.me/` (a public name resolving to 127.0.0.1), a name pointing at a cloud-metadata address, `https://[::ffff:127.0.0.1]/` or a redirect to an internal host all passed it.
- The helper checks the address at CONNECTION time (custom `lookup`, any private/loopback/link-local/CGNAT/ULA/mapped/NAT64/6to4/Teredo answer refuses the whole name, so DNS rebinding cannot swap it), judges IP literals itself (`net` never calls `lookup` for them), revalidates every redirect hop (3 max), and bounds the body (8 MiB while streaming) and the whole download (8 s). `isPrivateAddress` fails closed: anything that is not a well-formed IP literal counts as private.
- `listing-card-image.server.ts` then decides the format from the BYTES (`sniffUploadBytes`: JPEG/PNG/WebP/GIF only — SVG, AVIF/HEIF and TIFF, the decoders with the most `sharp` advisories, are refused and the card falls back to the placeholder) and calls `sharp` with `failOn: "error"`, `limitInputPixels: 40_000_000`; `data:` URLs get the same size cap before decoding.
- **Not migrated yet** (same hostname-only check): `lib/merchandise/generate-card.ts` (public `GET /api/merchandise/generate`) and `lib/photo-quality.server.ts`. Tests: `safe-remote-image`, `listing-card-image-source` (the older `listing-card-image.test.ts` covers the URL-picking helpers only).

## Virtual try-on — what is trusted and what is not

- **`?tryon=1` is honoured outside production only** (`lib/flags/try-on.ts`: `VERCEL_ENV`, else `NODE_ENV`). It is a query string anyone can add, so on the production deployment `TRY_ON_ENABLED=1` is the only way to turn the feature on. Previews and local dev keep the override for QA; for a full preview test set `TRY_ON_ENABLED=1` on the Preview environment (the API routes always use the strict flag `isTryOnFeatureEnabledStrict`, the override only shows the UI).
- **`POST /api/try-on/upload` is retired (410).** It was an anonymous upload to the PUBLIC blob store, unrate-limited, reachable with the kill switch off, and nothing called it. `lib/try-on/virus-scan.server.ts` is now unused.
- **The Replicate webhook body is never trusted** (`app/api/try-on/webhook/route.ts`). It used to check that some header existed (never its value) and finalise the job from `body.output`, which the server then downloaded and republished: a forged call was a full-read SSRF. Now only `body.id` is read, to find the job; status and output URL come back from Replicate with our token (`getTryOnJobStatus`). `REPLICATE_WEBHOOK_SECRET` is no longer read by the route — a real signature check (Svix) would only be defence in depth.
- **`fetchImageBytes` (try-on outputs and supplier-chosen garment URLs) goes through `fetchPublicImageBytes`**; `isVercelBlobUrl` tests the HOSTNAME, not a substring. `enforceTryOnIpRateLimit` falls back to the in-process limiter (5/min/IP) when Upstash is not configured — every call starts a paid Replicate prediction, so it must never be unlimited.
- **Not changed (privacy decisions for the owner)**: the shopper's selfie is stored on the public blob store (unguessable URL, deleted after the job and by the retention cron) unless `BLOB_TRYON_PRIVATE=1`; `GET /api/try-on?jobId=` / `prediction_id` answer without authentication (identifiers are not guessable). Tests: `try-on-flag-override`, `try-on-routes-hardening`, `try-on-image-fetch`, `try-on-rate-limit-fallback`.

## `proxy.ts` — reading the session, and what the proxy does NOT guard

- **Never call `getToken` directly in the proxy — use `readProxySessionToken(req, secret, secure)` and `resolveAuthSecret()` (`lib/proxy-session-token.ts`).** `getToken` throws `URIError: URI malformed` on a malformed `Authorization: Bearer` header when there is no session cookie (`@auth/core` 0.41.2, GHSA-xmf8), which made the page answer 500; the helper never throws and a missing secret or unreadable token is just "anonymous". `resolveAuthSecret` takes the FIRST NON-EMPTY of `AUTH_SECRET` / `NEXTAUTH_SECRET` like `env()` in `lib/auth.ts` — the proxy used `AUTH_SECRET ?? NEXTAUTH_SECRET`, so an EMPTY `AUTH_SECRET` hid a real `NEXTAUTH_SECRET` and the proxy silently stopped reading sessions while Auth.js kept working. `.env.example` documents `NEXTAUTH_SECRET` as the main variable. A missing secret is logged once at load (`[proxy] auth_secret_missing`).
- **The proxy's role-guard block is UNREACHABLE for the protected areas, and has been since 2026-05-21** (`95e49eef8` + `d4de0f649`). `proxy()` returns at `if (isStaticAppPathname(pathname))` BEFORE it, and `dashboard`, `admin`, `crm`, `marketplace`, `login`, `affiliate`… are all in `RESERVED_LOCALE_SEGMENTS`. So the redirects it contains — supplier / affiliate / agent / admin / CRM / buyer-account areas, signed-in users leaving `/login`, role-based `/marketplace` redirect, the legal re-acceptance gate (`legalGateOk`) — do not run today, with or without a secret. **Those areas are protected by their own layouts, pages and route handlers** (`requireSupplierSession`, `requireAffiliateSession`, `requireAdminSession`, the admin/CRM layouts, API guards), which is where any new protected page MUST check the session itself; do not count on the proxy. `proxy-guards.test.ts` pins this on purpose (the "NOT guarded by the proxy today" block): wiring the guard back is a product decision (it would also switch on every other dormant redirect, the legal gate included) and needs staging validation — change that test when you do.
- Pages with no guard of their own and no guarding layout (found 2026-11-01): `dashboard/affiliate/page.tsx` and `dashboard/products/[id]/page.tsx` (client shells whose data comes from authenticated APIs) and `agent/page.tsx` (public by design); the other `dashboard/admin/*`, `admin/*` and `crm` pages sit under a layout that checks the ADMIN role. Tests: `proxy-session-token`, `proxy-guards`.

## Stripe disputes, failed-webhook replay, cron failures (finalisation D7 / D2 / J1)

- **`charge.dispute.*` are handled by the dispute's STATUS** (`lib/stripe-dispute.ts`, called from the webhook processor; Stripe does not order events). Open (`needs_response`, `under_review`, `warning_*`, anything unknown) = every order of the charge is HELD: `Order.status = "disputed"` + an open row in the **dispute ledger = `ProcessedWebhook` rows with id `dispute:<dp_id>:<orderId>` and status `dispute_open|won|lost|closed`** (`lib/orders/dispute-hold.server.ts`, no migration; the previous status is kept in the `error` column as JSON). The payout release asks the LEDGER, not only the status, because tracking webhooks and supplier routes write `status: "shipped"` blindly: `process-transfers` (attempt stays PENDING, not cancelled), `triggerLightningPayout`, `payLegionOverrideForOrder`; `order-transfer-gating` has a `blocked_dispute` phase. Pure rules: `lib/orders/payment-state.ts` (`isOrderPayoutHeldForDispute`, `statusWhenDisputeOpens/Released`) and `lib/orders/dispute-state.ts`.
- **Won / closed without loss** restores the status the ledger remembers (refreshed when a later open event found the order moved on, e.g. shipped by a tracking webhook, and never behind the order's own shipped / preparing facts) — only if the order is still `disputed` (any casing), otherwise its current status is left alone and traced (`dispute_release_status_left`) — and closes the row. **Lost** is applied automatically ONLY when the disputed amount equals what our orders of the charge account for (±1 cent per order): Connect transfer reversals (`reverseConnectTransfersForRefund`, key `<dp>:<order>`), an `OrderStripeRefund` row `reason: "dispute_lost"` (what lets the `retry-pending-clawback` cron finish), the clawback ledger, then `REFUNDED` / `REFUND_PENDING_CLAWBACK`. A partial / oversize / other-currency dispute keeps the hold open and alerts a human (`skipped`, `dispute_lost_manual_review:<reason>`): to release one by hand, settle the order then set that ledger row's status. Stripe's dispute fee is allocated to nobody. Effects first, terminal ledger row last (a replay after a mid-way failure converges); a terminal row is never reopened. Events to enable on the Stripe webhook endpoint(s): `charge.dispute.created`, `.updated`, `.closed`, `.funds_withdrawn`, `.funds_reinstated`.
- **Failed Stripe events are replayed after Stripe stops retrying** (3 days): `GET /api/cron/replay-failed-stripe-webhooks` (every 6 h, `lib/cron/replay-failed-stripe-webhooks.ts`): `failed` rows with an `evt_` id older than 72 h and younger than 30 days, oldest first, `stripe.events.retrieve` then the SAME `processStripeWebhookEvent`; cap 20 / 40 s; a still-failing event = one ops alert + HTTP 500 (red run); older than 30 days or gone at Stripe = `failed_expired` + alert once. **Only a whitelist of event types is replayed late** (`REPLAY_SAFE_EVENT_TYPES` + `replayBlockReason` in `lib/stripe-webhook-replay.ts`: `checkout.session.completed` ONLY for a `mode: "payment"` marketplace session (not subscription / sponsor / blind-dropship / unreadable), `payment_intent.succeeded`, `charge.dispute.*`): `events.retrieve` returns the event as it was EMITTED, so the others (subscription snapshots and subscription checkouts that would revive a cancelled Pro/Radar/Growth plan, sponsor checkouts, `invoice.payment_failed`, `charge.refunded`, `account.updated`…) would write a stale snapshot over today's state: they are closed as **`failed_not_replayed`** unprocessed, with one alert (sent BEFORE the close) naming the reason. **To apply one on purpose: Stripe dashboard > Developers > Events > the event > Resend (or `stripe events resend EVENT_ID`)** — both webhook routes and the processor treat `failed` and `failed_not_replayed` as replayable by a delivery, and answer `duplicate` only for `failed_expired` (older than 30 days / gone at Stripe: it can not be resent). The cron selects `failed` only, so a closed row is never alerted twice.
- **Checkout fulfilment never re-enters an order that is paid or past paid, or closed** (`orderAwaitsCheckoutFulfilment`, `lib/orders/payment-state.ts`; gate `marketplaceCheckoutNeedsFulfillment`, also checked inside `ensureMarketplaceCheckoutFulfilled`): the gate used to say "any status but paid", so a replayed event re-ran the Ghost stock re-check on a SHIPPED order and could refund it. An event whose orders are all closed ends `skipped` / `orders_closed`. `statusAfterPaymentConfirmed` keeps every status the code writes after paid (`preparing`, `fulfilling`, `shipped`, `delivered`, `completed`, `returned`, `disputed`) and the closed ones, and the scheduler does not write the status at all when it does not change. In a lost-dispute handler (it runs inside the webhook transaction) every write to the Order row through the global Prisma client must come BEFORE `tx.order.update`, which locks the row until the event ends. Lightning, the Légion override and `process-transfers` all refuse a closed order (`isOrderClosedForPayout`) and an open dispute.
- **Crons**: `scripts/ci/run-crons.sh strict|lenient` runs the routes from `scheduled-crons.yml`. Money crons are `strict` (exit 1 on any curl error or non-2xx, no retry, no `|| echo WARN`) and their job has an `if: failure()` step (`scripts/ci/notify-cron-failure.sh`) that annotates and POSTs `/api/cron/notify-failure` (cron secret; the app posts to Slack/Discord through `lib/ops-webhook.ts`; body validated, bounded, mentions neutralised, `runUrl` must be a github.com Actions run; tolerant if the app is down). `lib/__tests__/cron-schedule-coverage.test.ts` fails on a `app/api/cron/*` route that is neither scheduled nor listed there as deliberately unscheduled with its reason, and on a money cron that is not strict: add the route to the workflow (or to that list) in the same change. **`/api/cron/sync-stock` is deliberately NOT scheduled — founder decision pending: what `Product.active` means.** It writes `active = (stock > 0)` for every product matching a partner SKU, so it would re-list a product a supplier paused (`PATCH active=false`) or that an admin recalled (`createRecall` sets `active=false`, GPSR). Decide first whether `active` is "listed by the supplier" (then the cron must only ever LOWER stock and deactivate, never activate) or "sellable"; also `review-invites`, `update-supplier-scores`, `verify-suppliers` (reasons in the test). `sync-auto-buy-tracking` IS scheduled (every 3 h, lenient) since the AliExpress tracking lookup exists (`lib/aliexpress-ds-tracking.ts`, G4): it marks shipped only an order still awaiting shipment (conditional update, tracking lock `partner`, tracking event, payout release check) and alerts — never moves — a refunded / cancelled / disputed order whose goods AliExpress shipped. The parsers were written from AliExpress's public documentation, not from a live answer.

### Pourquoi les pushs « s’interrompent » dans Cursor

Ce n’est pas un échec du commit : c’est souvent **`git pull --rebase` qui attend le réseau** (ou un prompt Git) dans une seule commande `commit && push:safe`. L’agent doit faire **deux appels shell** : d’abord `git commit`, puis `npm run push:safe -- <branche>` seul (**la branche nommée** : sans argument le script vise `main`, c’est-à-dire la production).

### Agent : commit + push après une correction

1. `git commit` (commande shell 1)
2. `npm run push:safe -- <branche-de-travail>` (commande shell 2, séparée ; **nommer la branche** — un `npm run push:safe` nu pousse `main` = production ; ne pas pousser du tout sans autorisation du fondateur quand le mandat dit « commits locaux uniquement »)

Puis une ligne : **Git** — Commit `abc1234` — *message* — push OK (`<branche>`). Détail : `.cursor/rules/git-commit-after-fix.mdc`.

Ce compteur **n’est pas Git** : il cumule les fichiers touchés **dans la conversation Agent en cours** (souvent 50+ sur une longue session).
Pour vérifier l’état réel : `npm run git:sync` (ou `git status`).
Pour **réinitialiser la liste** : démarre une **nouvelle conversation** Agent avant chaque nouveau lot de travail.

## Three systems, one hierarchy (founder principle 2026-11-18)

- **Affisell is first a supplier → reseller marketplace.** Three systems with separate responsibilities, in this order: (1) **Supplier Catalog** — supplier accounts, product sheets, offers, prices, stock, availability, commercial conditions, publication (`/api/supplier/products`, wizards, CSV import, `lib/listing-compliance`); (2) **Marketplace & Transaction** — the single reference for orders, amounts, commissions, fees and payment obligations (checkout, settlement, transfers, returns, disputes); (3) **Procurement** — a SECONDARY capability: external sources, quotes, automatic purchase only when the line's commercial model calls for it (`lib/suppliers`, `lib/auto-order`, `lib/fulfillment`).
- Boundaries: the transaction sells only what the catalogue published; procurement receives a line only after payment and only when its model requires a source purchase — **a supplier that manages its own stock never goes through procurement and nothing may require it to**; procurement reports facts (bought / refused / real cost / tracking), the transaction draws the money consequences; an imported product arrives as a DRAFT on a supplier account and passes the same publication gate as a hand-made sheet. Never spend catalogue / transaction effort on procurement-only work (design reference: the founder's doc « Moteur d'approvisionnement multi-sources Affisell », sections 0–0 ter).
- **Product lifecycle = three independent axes**: publication (`isDraft`: draft → published → withdrawn; supplier action or Affisell validation; imports always draft), commercial status (`active`: on sale / paused by the supplier / suspended by Affisell — today ONE boolean for both; since 2026-11-18 an OPEN product-safety recall is the suspension: `isProductHeldByRecall` (`lib/legal/recall-hold*.ts`, fails closed) refuses a supplier publish (`PUT /api/supplier/products/[id]`) or re-activation (`PATCH /api/products/[id]`) with 409 `product_recalled` — the classic form shows it in words (`supplier.publishBlockers.productRecalled`, 8 locales); since 2026-11-19 Affisell can also SUSPEND a product for any reason without migration (`lib/products/affisell-suspension.ts` pure + `.server.ts`: state `AuditLog` `product-suspension:<id>` + history `…:<n>`, closed reason list, admin `GET|POST /api/admin/products/<id>/suspension` `{action: suspend|lift, reason, note}`, panel « Statut commercial » on `/admin/products/<id>`); suspending sets `active=false` in the same transaction, LIFTING never re-lists (the supplier decides); both supplier activation paths call `checkSupplierMayActivate` (recall OR suspension, fails closed as `product_hold_unverifiable`) → 409 `product_suspended` explained in words (`supplier.publishBlockers.productSuspended`, 8 locales); a dedicated column remains the clean fix, migration = founder), availability (`stock`, variant stock, `lastStockStatus`). **Out of stock never unpublishes or deletes**; a technical failure never changes a status (it may block a payment, alert, mark availability unknown); availability checks happen BEFORE payment when the path requires it. ## Commercial (contract) models — chantier 5, DRAFT and SIMULATION only

- `lib/contract-models/model.ts` (pure): a model = the FIVE roles of a line (payer of the source, owner, contractual supplier, cost bearer, delivery & returns — never derived from one another; allowed combinations per path in `ALLOWED_ROLES`: A catalogue, B platform purchase, C1 delegated purchase, C2 advanced purchase) + parameters from a CLOSED list (no formula is evaluated), versioned (`id` + `version`, an order would keep the version of its payment). `validateContractModel` refuses forbidden role combinations, out-of-range rates, an advance outside C2, a C2 advance without guarantee or cap, and an ACTIVE model with undecided parameters. `splitLine` gives every party's share; path A reproduces today's settlement cent for cent (pinned against `unitOutcome`, itself pinned to the real settlement); every path conserves money and pays / deducts a source cost exactly once (tested over a grid).
- `drafts.ts`: v1 of the four models, all `draft`; every B / C value that changes who earns what is listed in `undecided` (placeholders for simulation, NOT proposals). `simulate.ts`: replays a model on past order snapshots and reports actual vs simulated totals — pure, writes nothing, never recomputes an order (no retroactive change).
- **Versions frozen per order** (`versions.ts`, pure, simulation): a published (id, version) never changes (`nextVersion` → version + 1, draft; `checkVersionUnchanged` refuses a different content under a used key); an order is governed by the assignment in force AT ITS PAYMENT (`resolveModelForOrder`: `effectiveFrom <= paidAt`, supplier-specific over global, most recent first; a back-dated assignment — `effectiveFrom < createdAt` — is ignored); before any assignment an order is `legacy` and `simulateAssignments` reproduces its frozen amounts unchanged. A test pins that adding / changing a FUTURE assignment never moves the simulation of past orders (`contract-model-versions`).
- **Sensitivity of the undecided rates** (`sensitivity.ts`, pure): an undecided rate of B / C1 / C2 is swept over a grid (0 → 30 %, a range to look at, NOT a proposal) and each party's total is shown with three thresholds — first value where Affisell's total after the ESTIMATED Stripe fee is ≥ 0, first value with no loss-making line, last value with no negative supplier share. **Replay on history** (`history-lines.ts` pure + `simulation.server.ts`, admin `GET /api/admin/contract-models/simulation?days=90`, READ-ONLY): path A on every usable paid order, paths B / C ONLY on auto-buy orders with a recorded AliExpress cost (the only real source costs known — none is invented for a catalogue order); refunded / disputed orders counted out. **Representative comparison** (`comparison.ts`, pure, part of the same report): REAL orders, one per price tercile (closest to the band's median — never an average), the four models side by side, each result labelled `recorded` / `missing` (a model needing an absent source cost is NOT computed) / `hypotheses` / `computed` / `risks`. Only PHYSICAL listings are managed. A product with variant rows whose line can not be tied to exactly ONE row is unmanaged too.
- **`CHECKOUT_STOCK_MODE` = `off` | `warn` (DEFAULT) | `enforce`**, read per request, same pattern as `LISTING_READINESS_MODE`. `warn` is a pure DRY RUN: the check before the payment only logs `would_refuse_insufficient_stock` and lets the buyer through; the fulfilment WRITES NOTHING to the stock (no decrement, no row lock — `Product.stock` is what the PDP, the showcase card and the JSON-LD read as "sold out", so a write would already change what shoppers see: a nominal-stock AliExpress product would be sold out by its first sale), computes from the snapshot it already loaded and logs `[stock] would_decrement` (before / after) or `[stock] would_drop` (the stock could not have served that paid line), and never removes a paid line. `enforce` is the only mode that writes: 409 before the payment, atomic decrement, and a paid line the stock can not serve becomes an unallocated line. `CHECKOUT_STOCK_GUARD=off` (also `0` / `false`) is the emergency valve and wins over the mode. **Before `enforce`: run `npm run report:checkout-stock` (READ-ONLY, uses the DATABASE_URL of `.env.local` — possibly production) and read the `would_drop` / `would_refuse` log lines.**
- **Before the payment** (`evaluateCheckoutStockGate`, shared by the cart checkout, the single-line checkout and `lib/agent-checkout.ts` — the agent's paid sessions reach the same decrement): in `enforce`, 409 `OUT_OF_STOCK` when nothing is left, 409 `INSUFFICIENT_STOCK` + `availableQty` otherwise, before the pending order and the Stripe session exist. These are Affisell's own codes: `OUT_OF_STOCK_VERIFIED` stays the supplier-probe refusal (its modal says "we just checked with our supplier" and hands out a coupon). The front end shows `cart.stock.*` (8 locales) from the code — in the buy-now hook (every caller: PDP, grid cards, discover, Pulse), the identity sheet and the cart page — never the raw code. `available` is the stock BEFORE the cart; lines sharing a product are counted together.
- **ONE rule for which variant is bought** (`lib/variant-selection.ts`, pure, NO import — founder briefs 2026-11-19): a variant = a row of `variants.variantRows`, with up to three dimensions — colour (name part before the first « / »), size (after it; any further part = `other`, a dimension no picker names) and storage (`attrs[<storage column>]`, column found by `isStorageCustomColumn` / the `stockage|capacity|…` key). Every dimension the buyer named must match; a size value that NO row has as a size is read as the capacity (the product page sends the capacity in the size slot when there is no size), never both. `resolveVariantChoice` → `resolved` (one row; with no choice only when the product has a single row) / `incomplete` + `missing` (a colour alone on a multi-size product, a phone with no capacity — never a size picked for the buyer, never « one row has stock » read as available) / `unknown` (the combination does not exist) / `duplicate_rows` (identical rows: the supplier's data — never refused, never decremented) / `no_rows` (no rows or table-only variants: not judged here). Used by the decrement (`planStockMovement`), the check before payment (`variantSelectionProblem`: `variant_unknown` / `variant_incomplete` / `variant_required`, with `missing`), the cart scope key (two spellings of one row share its stock), the size chips of the marketplace PDP (desktop + mobile) and the reseller boutique (`optionStockForChoice`: a combination that does not exist is sold out; while a dimension remains it is available as soon as one candidate has stock; `null` = no rows, the page keeps its product figure), the PDP buy / add buttons (`variantChoiceComplete`: blocked with `cart.stock.chooseOptions`, 8 locales) and the card / assistant buttons. **Capacity travels**: `normalizeCartVariantSignature(color, size, storage)` writes `g:<capacity>` ONLY beside a real size (otherwise the capacity stays in the size slot — existing signatures and cart rows keep their exact value); sent by the PDP buy-now / server cart add (`selectedStorage`) and the boutique (`commerce.selectedStorage`), and appended to the order's variant label so the supplier knows what to send. **Guest cart** (2026-11-19 §1): `GuestCartItem.selectedStorage` is kept as chosen, ONE signature builder `guestItemVariantSignature` (line id, cart page, blind checkout, merge on sign-in `mergeGuestCartLinesForUser` / `checkout/identified`) → the same `g:` signature as the server cart; a line saved before keeps its exact old signature (never rebuilt — it stays `variant_incomplete` for a product sold in capacities); the cart shows a « Capacité » chip (`cart.storageLabel`). **Table-only variants** (`ProductVariant` table, no advanced rows — §2): judged with the SAME rule through `variantsFromTable` / `rowsForChoice` (name « colour / size », a size alone keeps its slot, customData as attributes, the table's stock): the check before payment (`withTableVariants`, `lib/checkout-table-variants.server.ts`, one read-only query, only for `hasVariants` products, never throws) flags unknown / incomplete / missing choices and refuses a sold-out table variant in `enforce` (`findTableVariantShortfall`, advisory: the table is NEVER decremented); cards (`variant-choice` route) and the assistant read the table rows too (`requiresVariantChoice({ tableVariants })`); one table variant needs no choice. Orders labelled « Noir · M · 128 Go » are counted apart by the per-variant forecasts.
- **The check before payment** (`CHECKOUT_STOCK_MODE`, same gate as stock): `warn` (DEFAULT) logs `would_refuse_variant_*` with `missing` and refuses nothing; `enforce` refuses BEFORE the stock check: cart / single-line 409 `VARIANT_UNAVAILABLE` (`problem`, `missing`, `availableVariants` = rows with stock > 0 — the shopper chooses, nothing is swapped; `cart.stock.variantUnavailable*`), reseller boutique (`createResellerOrder` runs the shared gate: `variant_unavailable` / `out_of_stock` → 409, page refreshed, choice kept). **Choices that are missing, not refused** (every mode — a missing input, not a stock decision): card « buy » / « add » buttons (`addToBuyerCart`, `useBuyNowWithIdentity`) ask `GET /api/marketplace/listings/<id>/variant-choice` (public, read-only, rate-limited, one boolean, `requiresVariantChoice`: rows needing a choice, or ≥ 2 table-only variants) when they carry no choice, and send the shopper to the product page (`?choose=1` → `cart.stock.chooseOnPage`); a failed answer keeps the old behaviour. The assistant never pays for an undetermined variant (`variant_choice_required` + the product page). A single-row product with no choice is now decremented from its row in `enforce` (it can only be that one).
- **Paid, not shipped — what is deducted** (`lib/stock-exposure.ts`, read from the code 2026-11-19): in `enforce` the units are taken ONCE at payment (`reserveStockInTransaction`; a replay finds the order paid) and given back once on a closed never-shipped order; a supplier's form save applies only its own change (`stockBaseline`); forecasts subtract reserved units only when the platform does not deduct — no double deduction. In `warn` / `off` NOTHING is taken: the page shows the declared figure, which may still count units sold since (Affisell can not know whether the supplier updated it; subtracting them would deduct twice for one who did) — so no display correction is applied: `enforce` is the fix (founder decision). `report:checkout-stock` now measures it (`pendingOrders`: paid-unshipped units, products shown in stock whose declared units are all owed, owed beyond declared, units shown but already sold — second reading only) and the variant structure (`variantProductsNeedingChoice`, `…WithDuplicateRows`, `…WithUnnamedDimension`). Tests: `variant-selection`, `checkout-stock`, `checkout-stock-client`, `marketplace-checkout-stock-gate`, `agent-checkout-stock-gate`.
- **At payment processing, `enforce` only** (`reserveStockInTransaction`, `lib/checkout-stock.server.ts`): inside the fulfilment transaction, right before the order is written (or the pre-created order is paid): `SELECT … FOR NO KEY UPDATE` on the product row (the per-session advisory lock only serialises ONE checkout session, never two buyers; **not** `FOR UPDATE`, which also blocks the foreign-key check of every order insert of that product, including the checkout that pre-creates the order), then for a product-level movement `updateMany … WHERE stock >= qty` (never negative), for a variant row a rewrite of the RAW `variants` json (only that row's `stock` changes — never write back the parsed copy) and `Product.stock` kept in step. A multi-line cart first locks its physical products ONE BY ONE in ascending id order, so two carts with the same products in opposite order can not deadlock. The confirmation e-mails of a cart (and of a fresh single order) are sent after the commit, never while a product lock is held. It commits or rolls back WITH the order; a replayed event finds the order already paid: no double decrement. **Still inside the transaction**: the Medusa sync (`syncMarketplaceOrderToMedusa`, HTTP, part of the order's atomic state).
- **Stock given back for a closed, never-shipped order** (`lib/stock-restitution.ts` / `.server.ts`, cron `restore-closed-order-stock` every 30 min): in `enforce`, the fulfilment writes a reservation marker (`AuditLog` `stock-reserved:<orderId>`, same transaction as the decrement); the cron gives the units back once (`stock-restored:<orderId>`, under the product row lock) for an order closed per `isOrderClosedForPayout` that has no `shippedAt`, no tracking, no `supplierOrderId` and no ORDERED/SHIPPED/DELIVERED/PARTIAL fulfilment — to the variant row of the same name only (a vanished or ambiguous row is recorded, never credited elsewhere). Since 2026-11-18 it also refuses an order whose delivery was attested (`deliveredAt`) or that has a return request (`order_delivered` / `return_requested`): goods that reached the buyer go back to stock ONLY through an inspection recorded as resellable (`lib/return-disposition.ts`), never automatically.
- **Decisions for the founder (NOT implemented)**: (1) give the units back when a SHIPPED order is returned (business rule: is a returned item resellable?) — partial refunds and shipped/returned goods still leave the stock reduced (under-selling, never overselling); (2) a supplier saving the product form, or a catalogue / integration sync (`syncProductVariants` recomputes `Product.stock` from the table), overwrites the stock with its own value and resurrects sold units; (3) importers that write a nominal stock (AliExpress `stock > 0 ? stock : 1`, 99 / 999) with no scheduled refresh (J1): they will sell out after that many sales once enforced (in `warn` nothing is written, so they keep selling); (4) an unallocated line's buyer e-mail exists but is OFF until `UNALLOCATED_LINE_BUYER_EMAIL=true`; (5) a partial-allocation checkout's store-credit share. (1) and (2) are why the default is `warn`, which writes nothing.
- Tests: `checkout-stock`, `checkout-stock-client`, `unallocated-line`, `fulfil-unallocated-and-stock` (runs the real `fulfillMarketplaceStripeSession` AND the real settlement entry points on an in-memory database with rollback, `lib/testing/fake-checkout-db.ts`), `marketplace-checkout-stock-gate`, `agent-checkout-stock-gate`, `commission-refund-unallocated-line` (seeded trace + proof rows, as production has them), `stripe-sync-order-vat-unallocated`.

## AliExpress purchases — one gate for the three paths, and a margin floor (G2 + G3)

- **Every path that can place an AliExpress order calls `authorizeSupplierPurchase` first** (`lib/fulfillment/supplier-purchase-guard.ts`): the generic engine (`lib/suppliers/place-order-bridge.ts`, AliExpress adapter only), `lib/fulfillment/auto-buy.ts`, and `order.paid` / the manual `/api/orders/[id]/fulfill` route (`lib/aliexpress-fulfill-order.ts`). Five triggers still fire on every payment — on purpose; the gate, not the number of triggers, is what makes a double purchase impossible. **A new code path that buys on AliExpress MUST go through it** (lock → re-read → claim → margin), and must call `markSupplierPurchasePlaced` / `releaseSupplierPurchase` / `reportInDoubtPurchase` according to the supplier's answer.
- **How it works**: one transaction takes `pg_advisory_xact_lock(hashtext('affisell:supplier-purchase:<orderId>'))` (same mechanism as checkout fulfilment and the Medusa sync; the key is the ORDER, identical for the three paths), RE-READS the order, its `FulfillmentLog` and its engine jobs INSIDE the lock (`lib/fulfillment/supplier-purchase-decision.ts`, pure), and — only if nothing proves a purchase and nobody holds the claim — writes the durable claim `FulfillmentLog.status = BUYING`. The supplier call happens AFTER the commit, never inside a transaction. Evidence of a purchase = `Order.supplierOrderId`, a BOUGHT log, or an engine `SupplierFulfillmentOrder` carrying a supplier order id (not FAILED/CANCELLED) **that covers that order**. No schema change. Every write that does not hold the claim is conditional (`updateMany` on the status it read): a stale read can no longer erase a claim another path took.
- **Which order a job's supplier order id belongs to — ONE shared rule** (`lib/fulfillment/engine-job-attribution.ts`). The engine puts every order of a cart that goes to the same provider in ONE job with ONE `supplierOrderId`. **AliExpress** buys the job's FIRST line only (smallest `SupplierFulfillmentOrderLine.id`; the id is that one order's purchase, an assumption for jobs created before the gate); **every other provider** (CJ, blind REST…) sends all lines in one supplier order, so the id covers every line. Every reader uses that function and none may attribute `job.supplierOrderId` to all lines: the gate (`decideSupplierPurchase`), the refund-time cancellation (`attemptExternalOrderCancellation`: refunding the cart's second order does not cancel or flag the first one's purchase), `cancelSupplierFulfillmentJob` (on behalf of one order — `forOrderId` — a shared AliExpress job is never cancelled for a line it did not buy; only the explicit admin action on the job passes `allowSharedJob`; callers that say nothing are refused), the payout gate (`processOneAttempt`: the second order is not "upstream funded" by the first one's job) and `applySupplierPlaceOrderResult` (the lines an AliExpress job did not buy are flagged `MANUAL_REQUIRED` / `ae_group_line_not_purchased` instead of ORDERED; each is bought through `order.paid` / auto-buy under its own claim).
- **What an answer means is an ALLOW-LIST, not a deny-list** (`classifyPlaceOrderAnswer`, `lib/aliexpress-ds-create-order.ts`), read on EVERY text field of the answer (code and all message fields — never just the first non-empty one), with camelCase split (`ReadTimeoutException` → `READ TIMEOUT EXCEPTION`). **Definitive**: an explicit, recognised business refusal (address, stock/inventory, price, SKU, product offline, shipping, invalid phone/postcode, `A00*`) or a dead token, with no fault word anywhere in the answer. **Not processed, safe to try the next method**: unknown method / no permission / bad signature or timestamp, HTTP 401/403/404/405, a connection that was never made (DNS failure, refused connection). **Throttled, back off**: HTTP 429, the TOP throttle codes and wording. **Everything else is UNCERTAIN**: timeouts (`timed out`, `time out`, `timeout`), network errors where the request may have left (reset, socket timeout), unreadable or non-2xx answers (`strictHttpStatus`), **any ISP envelope (platform fault) whatever its text** (the gateway `type` is kept; a TOP `sub_code` starting `isp.` counts), a fault message (`FAULT_WORDS`: timeout, exception, unavailable, maintenance, overload, degraded, retry, remote, gateway, HTTP 5xx…) even if it also contains a business word, a gateway error whose text is not on the list, a 2xx without order id and without a recognised refusal. An uncertain answer is **never sent again** to another host/method (the AE payload has no idempotency key, so only this classification protects), the `BUYING` claim is kept, auto-buy skips its browser fallback and retry, the order.paid workers never retry it (`isNeverRetryFulfillError`, by prefix — whatever the text says), an alert goes out (Sentry `SUPPLIER_PURCHASE_IN_DOUBT:*` **and the ops webhook**) and the order is flagged `MANUAL_REQUIRED`. A claim NEVER expires into a new purchase (older than 15 min it is only reported `stale`). If the purchase succeeded but could not be written down (`placed_but_unrecorded`) the AliExpress id is in the alert — it is stored nowhere else. **What this guarantees**: for any answer that is not recognised as a refusal, the order is not sent again and the claim is not released. **What it does not**: the "definitive" side is a recognition by words — a platform fault worded in a way that neither the fault list nor an ISP envelope reveals, and that contains a business word, would be read as a refusal. The lists come from observed and documented answers, not from a proof; the other direction (a clean refusal worded in an unknown way) is escalated to a human, who has the reconcile action below.
- **A claim orphaned by a crash cannot alert itself** (the process is dead): the existing `sentinel-scan` cron (every 30 min, no new cron) runs `collectPurchaseInDoubtSignals` — every `FulfillmentLog` in BUYING for more than 15 min becomes ONE P0 signal `fulfillment.purchase_in_doubt` on its order (idempotent, closes by itself), and a NEW P0 is pushed to the ops webhook by `runSentinelScan`. The BullMQ worker never initialises Sentry, which is why the alerts above also go through `opsWebhookAlert` (`SLACK_WEBHOOK_URL` / `DISCORD_WEBHOOK_URL` — **if neither is set in the process that runs the purchases the alert is silent: the sentinel P0 in the admin UI is then the only signal**). The `order.paid` fast path reports a stale claim too.
- **Reconciling an order "in doubt" — the admin action** (after LOOKING at the AliExpress order list): `POST /api/admin/auto-fulfill/logs/<fulfillmentLogId>/reconcile` (admin session; also the « Réconcilier » button on a BUYING row of `/admin/auto-fulfill`), body `{ "outcome": "exists", "supplierOrderId": "<AliExpress order id>", "note": "…" }` or `{ "outcome": "not_exists", "note": "…" }`. `exists` records the purchase exactly like a normal one (`Order.supplierOrderId`, log BOUGHT: every path then answers "already placed"); `not_exists` releases the claim (log FAILED `RECONCILED_NOT_BOUGHT:…`: a retry may buy). It takes the SAME per-order lock as the gate, acts only on a log still BUYING, contacts nothing, buys nothing, and writes an `AuditLog` row (`auto_buy.reconcile_in_doubt`: who, what, which id, why) — no migration. The admin "retry" (`retryAdminAutoBuyFulfillmentLog`) still refuses a BUYING log (409 `purchase_in_doubt`; it used to reset one older than 10 min to PENDING and buy again). **Refunding an order whose purchase is in doubt** (SLA cron, lost dispute, admin refund) does not cancel anything (there is no order id): `attemptExternalOrderCancellation` flags the log `MANUAL_REQUIRED` (`purchase_in_doubt`) and alerts, so the human also checks AliExpress for an order to cancel.
- **Margin floor before any purchase** (`lib/fulfillment/auto-buy-margin.ts`, pure, integer cents): `margin = HT line − supplier transfer − affiliate transfer − estimated Stripe fee (2.9 % + 25 c on the TTC charge) − AE cost (unit price × quantity + shipping, of the SKU actually bought)`; the transfers come from the existing settlement functions (`computeTransferAmountsFromOrder`), so the gate cannot disagree with the payouts (`auto-buy-margin.test.ts` checks it against the real checkout functions over 576 combinations). Refused — never bought — when the margin is below `AUTO_BUY_MIN_MARGIN_CENTS` (default **300**; only a plain integer ≥ 0 is accepted, anything else falls back to 300), when it is negative whatever the floor, or when the cost/revenue is unknown: **a price ≤ 0 or a shipping ≤ 0 is UNKNOWN** — `SupplierLink.aeShippingCents` is `NOT NULL DEFAULT 0` and every importer writes 0, so a stored 0 means "never entered", not "free" (a truly free-shipping offer needs a deliberately conservative non-zero amount). The trace says WHICH part is unknown — `MARGIN_REFUSED:cost_unknown:margin=n/a:floor=300:missing=shipping` — and the alert says to enter the cost (lowering the floor or the price cannot fix an unknown cost). **Preflight, read-only: `GET /api/admin/auto-fulfill/links-missing-cost`** lists the active auto-buy links the gate will refuse (price / shipping / variant price of 0), to fix BEFORE enabling any autonomous purchase. **Known trap**: re-enlisting the same AliExpress product (`enlist-ae-product.ts`, update branch) rewrites `aeShippingCents` with the resolver's 0 — re-enter the amount afterwards. The 100-cent placeholder `enlist-ae-product.ts` writes on a variant when the AE price is unknown cannot be told from a real 1.00 EUR price: replace it with the real price. A refusal is traced (on the log, appended to the order's errors), alerted (Sentry warning + ops webhook) and flags the order `MANUAL_REQUIRED`. **The gate itself neither retries nor refunds** — but it does not suspend the buyer protections: `enforce-supplier-ship-sla` still auto-cancels and refunds any paid order with no tracking past its deadline (10 days + 3 days of grace by default), margin-refused orders included, and notifies the supplier and the affiliate as for any SLA breach. That is unchanged on purpose; the owner has that window to decide.
- **Re-running a margin refusal**: admin "Retry" and the Sentinel `retry-auto-buy` playbook answer **409 `margin_refused` with the trace** and change nothing (they used to flip the log to PENDING, erase the trace and enqueue a job the queue silently ignored because a finished job keeps its id). Sentinel reports a refused margin as `fulfillment.margin_refused` (open the order), not as a retryable failure. After fixing the price, the floor or the link's cost, re-run through `POST /api/orders/<id>/fulfill` (admin session or cron secret), which re-evaluates the margin.
- **Finding to decide (not hidden)**: the supplier payout is `wholesale − commission − supplier fee` and the AE cost is deducted from NO payout, so on an auto-buy line Affisell keeps `supplier fee + affiliate fee` and pays the AE cost out of its own pocket. With the current fees most lines will be refused by the floor until the owner decides who bears the AE cost. The gate reports what the code really does; it does not assume the model is right.
- **Not covered**: `POST /api/aliexpress/order/create` has no claim (no order id, secret-protected) — it now answers **409 `outcomeUncertain` + « vérifier avant toute nouvelle tentative »** and alerts on an uncertain outcome, but the caller is its only protection; lines 2..n of a multi-product AliExpress group in the engine (the adapter buys only the first line — an under-purchase, never a double one; the others are bought through `order.paid` / auto-buy, each under its own claim); the engine (sourcing channels) and `order.paid` paths are behind the single opt-in since 2026-11-18 (see « External purchases — ONE opt-in switch »); `stripe-invoice-payment-failed` cancels engine jobs without saying for which order (a shared AliExpress job is then refused, not cancelled); `autoBuyCardAmountCents` ignores the quantity; a finished BullMQ auto-buy job keeps its id, so a "retry" of a FAILED log can still enqueue nothing (pre-existing). Tests: `supplier-purchase-decision`, `supplier-purchase-guard` (in-memory lock that really serialises), `supplier-purchase-paths` (the three real paths at once), `aliexpress-ds-create-order-uncertain`, `aliexpress-ds-sync-strict-http`, `order-paid-no-retry-uncertain`, `auto-buy-margin`, `auto-order-apply-place-result`, `auto-order-engine-circuit-gate`, `orders-fulfill-route-gate-status`, `retry-auto-buy-in-doubt`, `external-order-cancellation`, `cancel-supplier-job-shared`, `process-transfers-job-attribution`, `reconcile-in-doubt-purchase`, `reconcile-in-doubt-route`, `links-missing-cost`, `aliexpress-order-create-route`, `sentinel/purchase-in-doubt`, `sentinel/run-scan-in-doubt`.

## Read-only reports — what they read, and the production lock (2026-11-18)

- `report:listing-readiness`, `report:checkout-stock` and `report:legacy-reseller-imports` go through ONE runner (`scripts/lib/read-only-report.ts`): it prints the target first (masked host, endpoint id, environment, which file DATABASE_URL came from, tables read, guarantees — `lib/reports/report-target.ts`, pure), then reads inside a `SET TRANSACTION READ ONLY` transaction on a client that refuses every non-read operation (`readOnlyPrismaClient` / `withReadOnlyTransaction`, shared with `report:fee-reconciliation`). `--target` = describe and exit, no connection. **A production (or unidentified) database is refused unless `--confirm-endpoint=<that endpoint id>`** — the written trace of the founder's authorisation (founder rule: no report on production without it). Staging / local run without it. The scripts never create their own client (`read-only-reports.test.ts`). Their collectors live in `lib/reports/*-report.ts` (relative imports only, no `@/lib/prisma`) and are RUN on the CI's real PostgreSQL inside the same read-only transaction (`read-only-reports-db.test.ts`: counts measured as before/after differences, nothing read changes) — the non-production proof before any production run. Pre-authorisation sheet: `docs/PRODUCTION-REPORTS-AUTHORIZATION.md`. **None has been run on production.**
- `report:legacy-reseller-imports` (`lib/reseller-import/legacy-inventory.ts` pure): reseller URL imports with no review tag — products live / draft, listings, resellers, 90-day and all-time paid orders, source hosts, import months, risks of LIVE products (no safety data, open recall, no photo, placeholder stock, empty description, zero price, unknown source). Aggregates only. Regularisation method: `docs/LEGACY-RESELLER-IMPORTS.md` (founder decisions).
